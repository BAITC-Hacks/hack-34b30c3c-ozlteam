# Расчёт пополнения склада

Домен `backend/app/Domains/Replenishment` реализует воспроизводимый расчёт для кейса
«Электрокомплект». Числа рассчитываются детерминированно, без LLM. Swagger `/docs` и
машинный контракт `/openapi.json` строятся из DTO, resources и контроллера домена.

## Запуск и получение результата

1. Загрузить справочники, продажи, остатки, ожидаемые поступления, подтверждённые
   интервалы stockout и прогноз прироста через DataImports/Integrations1C.
2. Завершить обмен источника (`complete=true`), чтобы расчёт не смешал части выгрузки.
3. С правом `replenishment.run` вызвать `POST /api/v1/replenishment/runs`:

```json
{
  "warehouse_id": "0195a27b-85a0-7000-8000-000000000001",
  "category_id": null,
  "as_of": "2026-09-01",
  "idempotency_key": "warehouse-september-2026-v1",
  "parameters": {"history_days": 1095}
}
```

UUID склада должен существовать в справочнике. Дата среза не может быть в будущем.
Ответ `202` содержит UUIDv7 расчёта и `job_id`. Статус задачи и прогресс доступны через
существующий Jobs API/SSE. Повтор с тем же ключом и параметрами возвращает тот же
расчёт; изменение параметров при том же ключе даёт `409`. Для нового расчёта, в том
числе после исправления ошибочного входа, передать новый ключ.

4. Читать состояние через `GET /api/v1/replenishment/runs/{id}`. Только `done` означает,
   что все рекомендации опубликованы. Для остальных состояний список результатов
   возвращает `409`. История: `GET /api/v1/replenishment/runs`.
5. Получить `GET /api/v1/replenishment/runs/{id}/recommendations`, затем подробное
   обоснование через `GET /api/v1/recommendations/{recommendation_id}`.

Списки поддерживают `limit` до 200 и `offset`; история — фильтр по складу,
рекомендации — фильтры по поставщику и срочности. `supplier_groups` содержит группы
**текущей страницы**, не всего расчёта. Количества в JSON — десятичные строки.
Право чтения — `replenishment.read`; данные общие для закупочного пространства компании.

## Фиксация входа и повтор фоновой задачи

Воркер получает JSON-срез через публичный Inventory service в транзакции. Источники
блокируются на чтение; импорт блокирует их на запись. В срезе сохраняются все реально
переданные источники, их ревизии, параметры и версия алгоритма `robust-daily-v2`.
Срез фиксируется при начале работы воркера, а не в момент HTTP-запроса. Последующие
обновления 1С уже не меняют этот расчёт.

CPU-работа вынесена из event loop в `asyncio.to_thread`. Все рекомендации и статус
`done` записываются одной транзакцией. Повторная доставка задания использует уже
зафиксированный срез; блокировка записи расчёта и уникальная пара «расчёт–товар»
предотвращают дублирование результата. При сбое сохраняется безопасное сообщение
ошибки без строк продаж и параметров SQL.

Историческая `as_of` ограничивает даты продаж/остатков. Это **не** восстановление
состояния учётной базы, каким оно было известно на ту дату: используются текущие
ревизии справочников и исправленных документов, зафиксированные в срезе. Для строгого
исторического backtest нужны архивные снимки источника.

## Алгоритм

### Регулярный спрос и выбросы

Продажи агрегируются по товару, дню и обезличенному клиенту. Возвраты учитываются в
нетто-количестве; отрицательный итог дня ограничивается нулём. Порог крупной покупки:

```text
max(5 × медиана положительных покупок,
    медиана + 8 × MAD)
```

MAD — медиана абсолютных отклонений. Покупка выше порога исключается из регулярного
спроса, но остаётся в исходном срезе и списке `excluded_sales` с датой, количеством,
порогом и причиной. Три и более крупных покупки того же клиента, охватывающие хотя
бы 28 дней, считаются повторяющимся спросом и сохраняются.

Если клиентских ID нет, используется дневная агрегация и явное предупреждение
`missing_client_ids_day_level_outliers_only`. Клиентские идентификаторы не выдумываются;
определение регулярных крупных закупок конкретного клиента в таком наборе недоступно.
Для товара с одной продажей статистически надёжное отделение выброса невозможно.

### Stockout

Периоды отсутствия включают обе границы; незакрытый интервал ограничен датой расчёта.
Для каждого такого дня оценивается спрос по доступным дням того же месяца и дня недели.
Если подходящих дней меньше трёх, используются все доступные дни того же дня недели,
затем общий средний спрос доступных дней. Коррекция не уменьшает реальные продажи.

Исходная и скорректированная история доступны отдельно; `lost_demand` показывает
добавленный спрос. Если все наблюдения относятся к stockout, строка блокируется:
нет данных для оценки. Месячные остатки сами по себе не превращаются в интервалы stockout.

### Сезонность и рост

- При истории от 540 дней определяется месячный профиль товара: средний спрос месяца
  относительно среднего за наблюдаемую историю. Коэффициент ограничен снизу 0,05.
- Для короткой истории используется усреднённый профиль товаров той же категории с
  достаточной историей **в выбранном срезе**. Если такого профиля нет, коэффициенты
  равны 1 и выводится `insufficient_history_for_annual_seasonality`.
- Базовый уровень — средний очищенный, скорректированный и сезонно нормализованный
  спрос за последние 56 дней. Нулевые дни после начала наблюдений учитываются.
- Устойчивый рост фиксируется, если три последовательных 28-дневных блока возрастают
  более чем на 2% каждый; необходимо хотя бы 21 наблюдение в каждом блоке. Дневной
  прирост ограничен `baseline / 180`. Оценка уровня переносится к дате среза.
- Внешний прогноз действует только в заданном периоде. Прогноз товара имеет приоритет
  над прогнозом категории, затем выбирается более поздняя дата начала. `additional`
  умножает прогноз со встроенным трендом на `1 + rate`; `replace_trend` отключает
  дальнейшую экстраполяцию тренда и применяет внешний прирост к уровню на дату среза.

Это объяснимый базовый алгоритм, а не утверждение доказанной точности на данных
партнёра. После получения репрезентативной истории нужны временной backtest, оценка
ошибки и настройка порога выбросов, страхового запаса и правила роста.

### Количество, сроки и срочность

```text
горизонт = срок поставки + период пересмотра
страховой запас = средний прогноз на горизонте × дни страхового запаса
доступный остаток = max(0, остаток − резерв)
потребность = max(0, прогноз + страховой запас − доступный остаток − поступления)
```

Период пересмотра и дни страхового запаса приходят из политики категории; Inventory
явно сообщает о резервной политике 7/7 дней, если категория отсутствует. Прогноз
начинается на следующий день после `as_of`. Страховой запас округляется до 6 десятичных
знаков до подстановки, чтобы сохранённая формула сходилась точно.

В поступления входят только подтверждённые/находящиеся в пути количества с датой
после среза и внутри горизонта. Просроченные поступления не считаются полученными;
выдаётся предупреждение. Баланс моделируется по дням: позднее поступление может
уменьшить заказ до нуля, но оставить критический дефицит до прибытия. При поступлении
в начале дня этот объём доступен для спроса данного дня.

Положительная потребность доводится до минимальной партии и округляется вверх до
кратности упаковки (в том числе дробной). В обосновании сохранены значение до
округления и прибавка. Если поставщик, срок поставки, история или остаток отсутствуют,
строка получает `status=blocked`; её нельзя превратить в заказ. Горизонт более
730 дней также блокируется. Остаток старше одного дня отмечается предупреждением,
поэтому менеджер должен проверить актуальность источника перед утверждением.

`critical` означает прогнозируемый дефицит до/в дату возможного прибытия нового заказа,
`high` — позднее внутри горизонта, `normal` — положительную потребность без дефицита,
`none` — отсутствие текущей потребности. Это приоритет по балансу, не вероятность.

## Заказы и обзор

Procurement использует публичный `get_recommendations_for_order()` для чтения и
блокировки готовых неизменяемых рекомендаций. Нельзя заказать заблокированную позицию
или позицию с нулевым количеством. Утверждение локального заказа не создаёт поступление
в пути; такое поступление подтверждается учётным источником.

`GET /api/v1/overview` показывает риски, избыток и проблемные позиции последнего
успешного расчёта выбранного склада (без фильтра — последнего расчёта вообще),
его версии источников и актуальное число черновиков. Это не сумма несовместимых срезов
разных расчётов. Детальная актуальность источников находится в DataImports/Integrations1C.

## Проверка

```sh
./scripts/dev.sh exec -T api pytest tests/test_replenishment_engine.py tests/test_replenishment_api.py
./scripts/dev.sh exec -T api ruff check app/Domains/Replenishment
./scripts/dev.sh exec -T api ruff format --check app/Domains/Replenishment
```

Синтетические тесты проверяют влияние каждого источника, сезонный пик, устойчивый
рост, восстановление stockout, устойчивость к разовому заказу, сохранение регулярных
крупных покупок, расчёт по неполным клиентским данным, запрет будущих продаж в истории,
сроки поступлений, дробную арифметику формулы, Swagger, права и идемпотентность API.
