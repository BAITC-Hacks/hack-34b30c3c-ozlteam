# Заказы поставщикам: backend-контракт

Домен `backend/app/Domains/Procurement` хранит черновики, корректировки, утверждённые
документы и отдельное подтверждение обработки документа системой 1С. Сам домен ничего
не отправляет поставщику или по сети в 1С. Утверждение не создаёт остаток, приход или
товар в пути: эти факты приходят из источников данных.

## Сценарий целиком

1. Загрузить и применить данные; выполнить расчёт пополнения. Использовать только
   рекомендации завершённого расчёта с положительным количеством и статусом `ready`.
2. `POST /api/v1/orders/from-recommendations` с выбранными `recommendation_ids` и
   `idempotency_key`. Создаётся отдельный черновик на каждую пару поставщик + склад.
3. Открыть `GET /api/v1/orders/{order_id}`. Проверить строки и при необходимости
   изменить количество через `PATCH /{order_id}/lines/{line_id}`. Передать текущую
   `expected_version` и обязательную причину `reason`.
4. Утвердить `POST /{order_id}/approve` с актуальной `expected_version`. Сервер
   проверяет право `orders.approve`, фиксирует автора, время и полный снимок заказа.
5. Скачать читаемый заказ через `GET /{order_id}/export?format=xlsx&layout=document`
   (так работают кнопки в карточке) либо получить JSON
   `GET /{order_id}/1c` для явной передачи адаптеру учётной системы.
6. Адаптер записывает результат обработки через `POST /{order_id}/1c/ack`.
   Это отдельное состояние интеграции; оно не меняет утверждённое содержание заказа.

### Документы заказа

`layout=document` формирует документ для сотрудника: названия поставщика и склада,
даты и редакция, комментарий, артикулы, коды 1С, полные наименования, единицы и
количества без лишних нулей. XLSX имеет русские заголовки, переносы, настроенные
ширины колонок и печать по ширине листа A4. Количества сохраняют точность; значения,
которые Excel не может хранить точно как число, записываются текстом. Цена и сумма
не выдумываются. CSV — плоская таблица с русскими колонками, разделителем `;`,
десятичной запятой и UTF-8 BOM; форматирование Excel в CSV не сохраняется.

`layout=exchange` — прежняя техническая таблица с `order_id`, `revision`,
`supplier_id`, `warehouse_id`, `sku`, `name`, `unit`, `quantity`. Это значение
по умолчанию для совместимости существующих клиентов API. Контракт JSON `/1c`
не меняется. Оба представления берут данные из утверждённого снимка; новая загрузка
справочников не меняет содержание ранее утверждённого документа. Короткая ссылка
заказа в печатной форме не является номером документа в 1С.

Права: чтение и аудит — `orders.read`; создание/изменение — `orders.write`;
утверждение — `orders.approve`; файл и пакет 1С — `orders.export`;
подтверждение 1С — `integrations.write`. Все endpoint требуют действующую сессию.
Рабочая область общая для компании: права на уровне роли, а не «только мои заказы».

## API

| Метод и путь относительно `/api/v1` | Назначение |
| --- | --- |
| `POST /orders/from-recommendations` | Создать список сгруппированных черновиков; 201 |
| `GET /orders` | Фильтры `status`, `supplier_id`, `warehouse_id`; `limit=1..100`, `offset>=0` |
| `GET /orders/{id}` | Полный заказ со строками, версией и реквизитами утверждения |
| `PATCH /orders/{id}` | Комментарий: `expected_version`, `comment`, `reason` |
| `PATCH /orders/{id}/lines/{line_id}` | Количество: `expected_version`, `quantity`, `reason` |
| `DELETE /orders/{id}/lines/{line_id}` | JSON-тело: `expected_version`, `reason`; возвращает обновлённый заказ |
| `POST /orders/{id}/approve` | JSON-тело: `expected_version`; фиксирует документ |
| `POST /orders/{id}/revise` | `expected_version`, `reason`; новая редакция только после явного отказа 1С |
| `GET /orders/{id}/audit` | Пагинация: `limit`, `offset`; автор, событие, время, до/после, причина |
| `GET /orders/{id}/export?format=csv` | Только утверждённый документ; CSV UTF-8 BOM или XLSX |
| `GET /orders/{id}/1c` | Версия схемы `1.0`, ключ дедупликации, снимок заказа и состояние передачи |
| `POST /orders/{id}/1c/ack` | `revision`, `status`, `external_document_id`, `message` |

Пример корректировки:

```json
{"expected_version": 1, "quantity": "125.500000", "reason": "Уточнена партия закупки"}
```

`quantity` — положительное Decimal с максимум 20 цифрами, из них до 6 после точки.
Количество, рекомендованное расчётом, хранится отдельно от исправленного количества.
Цена закупки не выдумывается и не включается в документ. Поля SKU, названия, единицы,
поставщика копируются в заказ; ссылка на рекомендацию/расчёт сохраняется для трассировки.
`external_references` фиксирует исходные `source_id` и `external_id` поставщика, склада
и каждой номенклатуры; у товара также сохраняются `code` и
`characteristic_external_id`. Адаптер 1С разрешает объекты по этим идентификаторам,
а не сопоставляет по SKU или наименованию. Реквизиты входят в неизменяемый снимок.

Подтверждение 1С:

```json
{"revision": 1, "status": "accepted", "external_document_id": "1c:purchase-order:123", "message": ""}
```

При `accepted` внешний идентификатор обязателен. Для `rejected` он необязателен;
сообщение содержит причину отказа. После отказа можно принять тот же документ,
только если ещё не создана новая редакция;
после принятия нельзя заменить внешний идентификатор или откатить состояние.
Идентичный повтор подтверждения возвращает прежний ответ, не создавая второго аудита.
Дедупликация на стороне адаптера: `order:{order_id}:revision:{revision}`.
Это согласованный внутренний JSON-контракт; совместимость с конкретной конфигурацией
1С требует маппинга полей по образцу партнёра и ещё не означает работающий сетевой обмен.

## Версии, конкуренция, повторное создание

`version` увеличивается при изменении комментария, строки, удалении строки и утверждении.
Проверка `expected_version` выполняется под блокировкой строки заказа. При конфликте
клиент получает 409 и должен перечитать документ. Утверждённый снимок неизменяем;
экспорт и чтение берут данные из снимка. `revision` — номер редакции документа,
начиная с 1. Утверждённый заказ никогда не открывается для правки повторно.

### Новая редакция после отказа 1С

`POST /orders/{id}/revise` требует `orders.write`, актуальную `expected_version` и
причину `reason`. Допустим только утверждённый заказ, для которого 1С явно ответила
`rejected`. Состояния `pending` и `accepted` запрещают новую редакцию (409): отсутствие
подтверждения не означает отказ. Создаётся **другой** заказ в статусе `draft`, с
`version=1`, `revision=предыдущая+1` и `supersedes_order_id`, с копией утверждённых строк
и внешних реквизитов. Старый снимок, автор и время утверждения остаются прежними.
Причина и связь документов записываются в аудит обоих заказов.

На предыдущий заказ берётся блокировка. Уникальность `supersedes_order_id` исключает
разветвление редакций. Повтор с той же версией и причиной возвращает существующую
следующую редакцию; другая причина даёт 409. Заявки на рекомендации не освобождаются:
копировать их можно только этой явной операцией. Новая редакция проходит обычную
проверку и утверждение, получает отдельное состояние передачи 1С и ключ
`order:{новый_id}:revision:{новая_редакция}`.

После появления следующей редакции старый заказ нельзя снова получить через `/1c`
или подтвердить как `accepted` (409 `order_superseded`). Идентичный повтор уже
записанного отказа остаётся идемпотентным. `/1c` также запрещён сразу после `rejected`
(409 `delivery_rejected`): для новой передачи необходимо выпустить редакцию. Это
исключает выдачу старого пакета параллельно созданию исправления. Исторические
`GET /orders/{id}` и CSV/XLSX остаются доступны; номер редакции указан в файле и имени.

На ключ создания и отсортированные ID рекомендаций берутся транзакционные advisory locks
PostgreSQL. В БД хранится хеш состава запроса и уникальная заявка на каждую рекомендацию.
Одинаковый ключ/состав возвращает созданные заказы; изменённый состав с тем же ключом —
409. Новый ключ с уже распределённой рекомендацией также даёт 409. Вся группа заказов
и аудит сохраняются атомарно одной транзакцией. Удаление строки не снимает заявку:
повторная закупка по той же рекомендации не должна появиться незаметно.

Ограничение: заявка защищает конкретный ID рекомендации, а не все будущие расчёты
одного артикула. До нового заказа необходимо обновить подтверждённые данные из 1С и
проверить действующие заказы. Локальное утверждение нельзя автоматически считать
подтверждённым товаром в пути, иначе возникнет двойной учёт после синхронизации.

## Экспорт и ошибки

Документ для менеджера (`layout=document`) содержит названия поставщика и склада
на момент утверждения и читаемую таблицу товаров; полный UUID заказа вынесен отдельно.
Техническая таблица (`layout=exchange`) сохраняет прежние колонки идентификаторов;
в ней Decimal хранится текстом без преобразования во float, XLSX ячейки явно текстовые.
Оба варианта используют утверждённый снимок. В CSV значения,
которые могут быть формулами, получают начальный апостроф. Для машинного обмена
использовать JSON-пакет с исходными значениями. Ответ содержит Content-Disposition,
Cache-Control: no-store и X-Content-Type-Options: nosniff.

Значимые ошибки: 401 — нет сессии; 403 — нет права; 404 — неизвестный объект;
409 — `version_conflict`, `order_immutable`, `already_allocated`,
`supplier_unavailable`, `recommendation_blocked`, `approval_required`,
`revision_conflict`, `delivery_conflict`, `revision_requires_rejection`, `revision_exists`,
`order_superseded`, `delivery_rejected`; 422 — некорректный запрос.
Актуальные схемы, статусы и media types опубликованы FastAPI в `/openapi.json` и `/docs`.

## Интеграция и проверки

Маршрутизатор: `app.Domains.Procurement.controllers.http.router`, prefix `/api/v1`.
Модели: `Order`, `OrderLine`, `OrderAllocation`, `OrderCreation`, `OrderAudit`, `OrderDelivery`.
Регистрация в общем `app.models` и новая Alembic-миграция обязательны.
Новые технические UUID генерирует PostgreSQL 18 `uuidv7()`; `OrderAllocation` использует
уже существующий UUID рекомендации как естественный первичный ключ.

Публичные зависимости: `get_recommendations_for_order(session, ids)` из Replenishment
и `get_suppliers(session, ids)`, `get_external_references(session, product_ids,
supplier_id, warehouse_id)` из Catalogs, подключённые через адаптер без ORM-импортов.
Публичный метод для обзора: `count_draft_orders(session, warehouse_id=None)`.

```sh
./scripts/dev.sh exec -T api pytest tests/test_procurement.py
./scripts/dev.sh exec -T -e RUN_DB_TESTS=1 api pytest tests/test_procurement_database.py
./scripts/dev.sh exec -T api ruff check app/Domains/Procurement tests/test_procurement.py tests/test_procurement_database.py
```

БД-тест требует применённых миграций, создаёт собственные записи, проверяет параллельные
запросы и удаляет только их. Проверяются группировка, идемпотентность, конкурирующие
изменения, запрет утверждения без права, неизменяемый снимок, точность экспорта,
защита от формул и отдельное идемпотентное подтверждение 1С.
