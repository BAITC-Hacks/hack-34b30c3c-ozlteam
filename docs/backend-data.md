# Учётные данные, импорт и обмен с 1С

Бэкенд принимает нормализованные данные по HTTP и из CSV/XLSX. Это работающий контракт
приёмника обмена, а не подключение к неизвестной конфигурации 1С партнёра. Конкретный
адаптер на стороне 1С, расписание и формат её документов согласуются после обследования базы.
API описано в `/docs` и `/openapi.json`; префикс всех маршрутов — `/api/v1`.

## Идентификаторы и границы

- Внутренние ID — PostgreSQL 18 `uuidv7()`, тип `uuid`. Время в UUID не заменяет даты документов.
- Идентичность объекта: `(source_id, external_id)` в пределах вида данных. `source_id` означает
  конкретную базу 1С, `external_id` — стабильный ID объекта или строки источника. Он может быть
  GUID либо другой строкой, но не должен зависеть от изменяемого наименования или артикула.
- Артикулы, коды и внешние ID остаются строками: ведущие нули и суффиксы не теряются.
- Каждая характеристика товара моделируется отдельной позицией с устойчивым составным
  внешним ID, например GUID номенклатуры + GUID характеристики. Исходный ID характеристики
  дополнительно хранится в `characteristic_external_id`.
- Одна компания, общие корпоративные данные по правам роли. Изоляция нескольких арендаторов
  и ограничения отдельных пользователей по складам не реализованы.
- Существующий товар обновляется без смены внутреннего UUID. `source_revision` — версия
  объекта, `source_updated_at` — время изменения в источнике, `created_at/updated_at` — время у нас.
- Даты продажи, документа, снимка остатка и ожидаемого поступления — разные поля. Моменты
  времени передаются с часовым поясом. Количества — Decimal в базовой единице товара.

## Первоначальный и последующий обмен

1. Пользователь с правом `integrations.write` создаёт источник:
   `POST /integrations/1c/sources`, тело `{"name":"1С: основная база","system":"1c"}`.
2. Полученный UUID подставляется в `POST /integrations/1c/sources/{source_id}/batches`.
3. Каждая порция содержит `batch_key`, `expected_revision`, непрозрачный `cursor`, флаг
   `complete` и до 10000 типизированных строк. При первоначальной загрузке `expected_revision=0`.
4. Полученная версия источника используется как `expected_revision` следующего пакета.
   Одинаковый `batch_key` и полностью одинаковое тело возвращают прежний результат без записи
   дублей, даже если источник уже получил более поздние пакеты. Изменённое тело с прежним
   ключом, устаревшая версия источника или конфликт версии строки дают HTTP 409.
5. Для многочастной согласованной выгрузки все промежуточные пакеты имеют `complete=false`.
   Только последний — `complete=true`. До завершения расчёт блокируется с HTTP 409.
   Нельзя выставлять `true`, пока продажи, остатки и ожидаемые поступления относятся к
   несовместимым состояниям базы. Этот флаг — обязательство отправляющего адаптера.

Пример полного пакета (ссылки внутри него разрешаются независимо от порядка строк):

```json
{
  "batch_key": "initial-2026-09-23-001",
  "expected_revision": 0,
  "cursor": "source-change-42",
  "complete": true,
  "rows": [
    {"kind":"categories","external_id":"cat-1","revision":1,"name":"Кабели","review_days":7,"safety_days":5},
    {"kind":"suppliers","external_id":"supplier-1","revision":1,"name":"Поставщик"},
    {"kind":"warehouses","external_id":"warehouse-1","revision":1,"name":"Основной","organization_external_id":"org-1"},
    {"kind":"products","external_id":"product-1","revision":1,"sku":"000123_","code":"000123","name":"Кабель","unit":"м","category_external_id":"cat-1","supplier_external_id":"supplier-1","lead_time_days":14,"pack_size":"1","min_order_qty":"0"},
    {"kind":"sales","external_id":"sale-1:line-1","revision":1,"product_external_id":"product-1","warehouse_external_id":"warehouse-1","date":"2026-09-01","document_id":"sale-1","line_id":"line-1","quantity":"12","client_id":null,"status":"posted"},
    {"kind":"stocks","external_id":"stock-20260923-product1","revision":1,"product_external_id":"product-1","warehouse_external_id":"warehouse-1","as_of":"2026-09-23T09:00:00+05:00","quantity":"20","reserved":"3"},
    {"kind":"inbound","external_id":"purchase-1:line-1","revision":1,"product_external_id":"product-1","warehouse_external_id":"warehouse-1","supplier_external_id":"supplier-1","document_id":"purchase-1","expected_date":"2026-10-01","quantity":"10","status":"confirmed"},
    {"kind":"stockouts","external_id":"stockout-1","revision":1,"product_external_id":"product-1","warehouse_external_id":"warehouse-1","start":"2026-08-05","end":"2026-08-08"},
    {"kind":"growth","external_id":"growth-1","revision":1,"category_external_id":"cat-1","start":"2026-09-01","end":"2026-12-31","rate":"0.1","mode":"additional"}
  ]
}
```

Для исправления передаётся полная строка с тем же `external_id` и более высокой `revision`.
Уже применённая версия с тем же содержимым не меняет данные; та же версия с другим
содержимым отклоняется. Возврат отражается отрицательной продажей. Отмена продажи —
`status=cancelled`; отмена поступления — `status=cancelled`; справочник деактивируется
через `active=false`. Ошибочный интервал stockout или прогноз отменяется новой версией
с `active=false`, и перестаёт участвовать в расчёте. Физические удаления не предусмотрены.

Один документ/строка продажи не может быть повторно записан под другим внешним ID в том же
складе и источнике. Аналогично запрещены два внешних ID одного снимка товара на один момент.
Пересекающиеся активные прогнозы роста для одного товара или одной категории отклоняются;
новая версия того же прогноза заменяет старую. Прогноз категории и отдельного товара могут
сосуществовать: приоритет выбирает расчётное ядро. `rate=0.1` означает 10%, не число 10.
`additional` дополняет наблюдаемый тренд, `replace_trend` заменяет его.

Справочники имеют чтение списка/объекта, POST и PATCH с полной версионированной строкой
в `/catalogs/{products|categories|suppliers|warehouses}`. PATCH не меняет идентичность источника.
Товар имеет одного основного поставщика и его срок поставки; выбор между несколькими
предложениями поставщиков пока не реализован. Отсутствующий срок или поставщик не выдумывается.

## Файлы: проверка перед применением

`POST /imports` принимает multipart:

| Поле | Смысл |
| --- | --- |
| `source_id` | Зарегистрированный источник |
| `kind` | Один из девяти видов строк из примера |
| `file` | CSV UTF-8 либо XLSX, до 25 МиБ и 10000 непустых строк |
| `column_mapping` | JSON-словарь: исходный заголовок → поле строки; по умолчанию `{}` |
| `quantity_multiplier` | `1` по умолчанию; `-1` только при явно выбранном обратном знаке источника |

Первая строка каждого листа — заголовок. Учитываются все листы. Числовые Excel-ячейки
не могут сохранить уже потерянные в файле ведущие нули; коды нужно передавать текстовыми.
Без сопоставления названия колонок должны совпадать с DTO, лишние поля отклоняются.
При сопоставлении только выбранные колонки попадают в staging; остальные не сохраняются.
Строка не может переопределить выбранный `kind`. Preview содержит до 20 типизированных строк.
Ошибки содержат лист, номер строки, поле и причину, без исходных значений персональных данных.
Исходный файл не сохраняется: остаются нормализованные строки и SHA-256.

Сначала загружаются справочники, затем факты. Пример CSV для категории:

```csv
external_id,revision,name,review_days,safety_days
cat-1,1,Кабели,7,5
```

`POST /imports/{id}/apply` с телом `{"complete":false}` применяет проверенный набор целиком.
На последней согласованной части передайте `true`. Между stage и apply версия источника
не должна измениться: иначе HTTP 409 и нужна повторная проверка. Повтор уже применённого
импорта безопасен. Ошибочный импорт остаётся в истории, а рабочие данные не меняются.
Прежний курсор источника при файловом импорте сохраняется.

Разбор файла выполняется в рабочем потоке, но HTTP ждёт результата; это ограниченный
синхронный импорт, без обещания фоновой загрузки миллионов строк. Для больших наборов
нужны нормализация и разбиение на пакеты. Анализ реальных исходников партнёра —
в [TrackLogic](hackathon/tracklogic.md). Их исходящие продажи записаны отрицательными,
клиентов и цены нет, а месячные начальные остатки не задают интервалы stockout. Такие
файлы нельзя автоматически считать готовым нормализованным контрактом.

## Согласованность, доступ и наблюдение

Каждое применение блокирует строку источника и проходит одной транзакцией. Справочники,
факты, версия, курсор и журнал фиксируются вместе; ошибка откатывает весь пакет.
Получение расчётного snapshot удерживает shared locks источников до сохранения снимка
расчёта, поэтому новый обмен не подменит данные посередине чтения. История расчёта
сохраняет JSON snapshot и версии источников; исходные таблицы содержат текущие редакции
объектов, а не полный архив каждой редакции документа. Повторный расчёт «на прошлую дату»
использует доступные сейчас исправленные исходные данные; воспроизведение прежнего
результата опирается на сохранённый snapshot расчёта.

`GET /inventory` показывает последний остаток по складу и товару; `/inventory/stocks`
показывает историю снимков. `/inventory/{sales|inbound|stockouts|growth}` предоставляет
источники, включая отменённые записи для аудита. Расчёт использует действующие записи.
Все списки фактов имеют limit/offset и фильтры по товару/складу (рост задаётся товаром/категорией).

`GET /integrations/1c/sources` возвращает версию, курсор, complete и время синхронизации.
`GET /integrations/1c/sources/{id}/batches` — журнал успешно применённых пакетов с автором
в хранилище и числом созданных/обновлённых/неизменных строк. Отклонённые попытки возвращают
структурированную HTTP-ошибку и не создают успешный журнал или новый курсор.

Необходимы права `catalogs.read/write`, `inventory.read`, `imports.read/write`,
`integrations.read/write`. Авторизация — существующая сессия пользователя; отдельные
машинные токены, ротация ключей и исходящий вызов HTTP к партнёру сюда не входят.
Продажи принимают только необязательный обезличенный `client_id`, не ФИО/email/телефон.
Формат поля ограничен, но поставщик данных обязан обезличить идентификатор до передачи:
по произвольной строке невозможно доказать отсутствие персональных данных.

## Публичные Python-контракты

- `Inventory.services.inventory_service.get_snapshot(session, warehouse_id, category_id, as_of)`:
  JSON-совместимые `products`, `sales`, `stocks`, `inbound`, `stockouts`, `growth`,
  `source_versions`, `warnings`. UUID/Decimal/даты сериализованы в строки. Неверный склад
  или категория дают 404; незавершённый источник — 409. Нехватка источников отражается
  предупреждениями, отсутствующие остатки и сроки не маскируются.
- `Catalogs.services.catalog_service.get_suppliers(session, supplier_ids=None)`:
  список поставщиков с внутренней и внешней идентичностью.
- `Catalogs.services.catalog_service.get_external_references(session, product_ids, supplier_id,
  warehouse_id)`: supplier, warehouse и список products с `source_id/external_id`.
  Заказ сохраняет эти ссылки в утверждённой редакции, а не перечитывает для каждого экспорта.

Проверки: `pytest tests/test_data_imports.py`, затем на Compose-БД после миграций
`RUN_DB_TESTS=1 pytest tests/test_data_database.py`. Тесты БД откатывают свои транзакции.
