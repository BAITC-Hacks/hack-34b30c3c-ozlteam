# AI-помощник закупщика: устройство и работа

Состояние реализации на 23.09.2026. Документ описывает код, а не обещает промышленную
приёмку на данных партнёра. Направление продукта — [пополнение склада
Электрокомплекта](../PROJECT_DIRECTION.md); входные данные и ограничения —
[общий контекст](../CONTEXT.md).

## Что реализовано

Один главный агент-координатор и пять тематических помощников работают через общий
чат `/assistant` и боковую панель. Это шесть профилей одного backend-движка с разными
инструкциями и серверными списками разрешённых инструментов. Они не являются шестью
отдельно развёрнутыми сервисами, параллельными автономными процессами или агентами,
которые продолжают работу без запроса пользователя.

| Профиль | Задача | Допустимое действие с подтверждением |
| --- | --- | --- |
| Главный закупщик `auto` | Выбирает одного тематического помощника по вопросу | Передаёт запрос специалисту; собственных операций записи нет |
| Справочник `help` | Объясняет экраны и правила по локальной базе справки | Нет |
| Данные 1С `data` | Находит пакеты, показывает статус и агрегированную готовность | Применение уже проверенного пакета |
| Запасы `inventory` | Проверяет остатки, резерв и ожидаемые поступления | Нет |
| Спрос и расчёт `demand` | Читает расчёты, рекомендации и сохранённое числовое объяснение | Запуск нового фонового расчёта |
| Заказы `procurement` | Читает заказы и рекомендации, готовит состав черновиков | Создание черновиков из готовых рекомендаций |

Можно оставить автоматический выбор или выбрать специализацию вручную. Количества
вычисляет существующий детерминированный алгоритм, не LLM. Изменение специализации
не даёт сотруднику дополнительных прав.

## Как проходит запрос

```text
Страница /assistant или боковая панель — один выбранный диалог
    -> проверка входа и владельца диалога
    -> координатор или выбранный помощник
    -> JSON-план модели -> проверка схемы, инструмента, UUID и прав в Python
    -> существующие бизнес-сервисы -> ограниченные сводки
    -> ответ + журнал инструментов + источники
       либо предложение действия с серверным предпросмотром
    -> отдельная кнопка подтверждения
    -> повторная проверка -> бизнес-операция -> результат/ID фоновой задачи
```

Движок использует общий интерфейс `LlmProvider.complete`: модель возвращает один
JSON-шаг, а Python проверяет его по закрытым Pydantic-схемам. Это provider-neutral
протокол планирования, не зависимость от нативного function calling одного провайдера.
Доступны настроенные адаптеры OpenAI, Anthropic, NVIDIA и совместимого API; конкретная
модель должна поддерживать следование JSON-инструкциям. Наличие адаптера не означает
проверку качества всех моделей.

На вопрос допускается до четырёх шагов планирования/инструментов, плюс выбор
специалиста и итоговое объяснение. UUID разрешены только из пользовательского
контекста/вопросов или полученных результатов. Если ID неизвестен, сначала нужен
поиск; неоднозначный выбор требует уточнения. Неверный план или запрещённый
инструмент не исполняется. Посторонние вопросы кратко возвращаются к теме закупок.

## История и контекст

На странице и в плавающей панели сначала видны чат и ввод. «История» открывает
отдельный список диалогов, «Контекст» — компактное окно выбора склада/пакета и
явного согласия на передачу сводок. На телефоне используется общий нижний sheet.
Ручной выбор темы скрыт в дополнительных настройках; по умолчанию работает
автоматический подбор. Статус разрешения и выбранный контекст видны над чатом,
даже когда окно настроек закрыто. Открытие этих окон не сбрасывает черновик.
Плавающая мини-планета доступна только вне `/assistant`; на мобильной странице
помощника её заменяет обычная иконка навигации. Большая планета показывается
в приветствии пустого диалога и исчезает, когда в нём появляются сообщения.

PostgreSQL хранит диалоги, сообщения, выбранного помощника, журнал инструментов,
ссылки на справку и предложения с решениями. Диалоги личные: чужой ID возвращает
404. Страница и панель используют общий компонент и состояние выбранного диалога.
После перезагрузки история читается с сервера; в `sessionStorage` хранится только
ID выбранного диалога, не текст переписки.

Неотправленный текст хранится отдельно для каждого диалога в памяти текущего
пользовательского сеанса. Он сохраняется при переходах между разделами и общей
страницей/плавающей панелью; переключение диалога возвращает его собственный черновик.
После успешной отправки очищается только отправленный текст — вопрос, дописанный
во время ожидания, остаётся. При ошибке черновик не стирается. Выход из аккаунта
или полная перезагрузка страницы очищает эти локальные черновики; между вкладками
браузера они не синхронизируются. В browser storage текст не записывается.

Новый ответ появляется плавно, с аккуратными абзацами и переносами. История не
проигрывает анимацию повторно; настройка reduced-motion показывает текст сразу.
Кнопка «Показать полностью» пропускает эффект. Это визуальное раскрытие уже
полученного ответа, не потоковая генерация от сервера. Содержимое остаётся безопасным
обычным текстом: HTML/Markdown не исполняется и не превращается в произвольные ссылки.

Показываются последние 100 сообщений с загрузкой предыдущих; список диалогов
постраничный. Название нового диалога формируется из первого вопроса. Интерфейса
переименования, удаления, общего командного доступа или поиска по переписке пока нет.

В раскрывающемся блоке можно выбрать склад и пакет. Контекст рекомендации, заказа,
расчёта и пакета также принимается из поддерживаемых URL-параметров; на странице
рекомендации берётся ID из пути. Контекст — подсказка агенту, не новая модель
складской изоляции: доступ к корпоративным объектам определяется существующими
предметными правами. Нельзя считать выбранный склад отдельной границей безопасности.

## Инструменты

Всего 13 инструментов чтения, распределённых между помощниками:

- `search_help` — локальная редакционная справка;
- `search_catalog` — товары, склады, поставщики и категории;
- `get_overview` — сводка закупок;
- `get_stock`, `get_inbound` — остатки и ожидаемые поступления;
- `list_runs`, `get_run` — история и статус расчётов;
- `list_recommendations`, `get_recommendation` — рекомендации и объяснение;
- `list_orders`, `get_order` — заказы и ограниченный состав;
- `list_packages`, `get_package` — пакеты и агрегированная готовность.

Списки ограничены страницами до 20 записей. Сумма показанной страницы не является
итогом всего склада. Пакет отдаётся без сырых строк и файлов: статус, счётчики,
число проблем и распределение `ready/limited/blocked`. Построчные ошибки и настройка
сопоставлений остаются на `/data`; чат не заменяет полный экран качества данных.

Три вида предложения проходят отдельную операцию подтверждения:

| Вид | Предпросмотр | После подтверждения |
| --- | --- | --- |
| `calculate` | Склад, категория, дата среза, глубина истории | Создаётся фоновый расчёт; доступны ID расчёта и задачи |
| `create_orders` | До 20 готовых рекомендаций, товары, количество, поставщик и склад | Создаются черновики, сгруппированные по поставщику и складу |
| `apply_package` | Проверенный непустой пакет, счётчики и готовность | Запускается применение пакета к рабочей базе; блокировки качества сохраняются |

В чате это наши компоненты предпросмотра и кнопки «Подтвердить действие» / «Отменить
предложение», не HTML или исполняемая форма от модели. Предпросмотр сейчас не
редактируется: для другого состава запросите новое предложение; количество
созданного черновика корректируется штатным процессом заказов. Редактируемые
динамические формы не заявлены реализованными.

## Почему обязательно подтверждение

Модель предлагает действие, но не получает инструмент самостоятельной записи.
Сервер сам строит предпросмотр из бизнес-данных. Кнопка отправляет ID предложения,
решение и ожидаемую версию, а не произвольный изменённый payload из браузера.

При подтверждении заново проверяются владелец, версия, предметные права,
актуальность предпросмотра и допустимость операции. Изменившиеся данные дают 409:
нужно запросить новое предложение и проверить его. Повтор того же решения не
создаёт второй заказ; для бизнес-операции используется ключ предложения.
Повтор сообщения также защищён `client_request_id`: тот же ключ нельзя использовать
с другим содержимым. Одновременно выполняется одно AI-действие пользователя.

Подтверждение запуска фоновой задачи не означает, что расчёт или импорт уже
завершён успешно. Статус нужно смотреть в исходном разделе. Подтверждение создания
черновика не утверждает заказ и не отправляет его поставщику. Утверждение и экспорт
остаются штатными действиями на `/orders` с отдельными правами.

## Справка / RAG

Реализован небольшой локальный retrieval-контур: девять проверенных текстовых тем
в `knowledge_service.py`, поиск по русским/английским ключевым префиксам, не более
трёх фрагментов, затем ответ модели с источниками. Темы: навигация, нормализованный
импорт, исходные Excel, REST 1С, расчёт, остатки, заказы, идентификаторы и безопасность.
Ссылки источников ведут на соответствующие рабочие экраны. Корпус доступен через
авторизованный `GET /api/v1/ai/knowledge`.

Это keyword retrieval, **не семантический поиск**: эмбеддинги, индекс pgvector,
загрузка пользовательских регламентов и поиск по коммерческим книгам не подключены.
Неизвестная тема возвращает пустую выборку; модель должна сообщить об отсутствии
подтверждённого ответа. При изменении экранов следует обновлять редакционные статьи.

## Данные, согласие и безопасность

По умолчанию `allow_business_data=false`: доступна только справка; автоматический
режим выбирает справочника. Для чтения учётных сводок пользователь явно включает
разрешение в чате. При этом ограниченные, отобранные backend поля передаются
настроенному LLM-провайдеру. Полные Excel, сырые продажи, внутренние credentials и
произвольные ORM-поля этим агентным контуром не отправляются.

Сам текст введённого вопроса отправляется модели и без этого флажка: не вставляйте
секреты или чувствительные строки вручную. Отзыв разрешения не стирает ранее
сохранённую историю и не отзывает уже переданные провайдеру данные. Предыдущие
сообщения с учётным контекстом не переиспользуются как обход текущих прав:
нужные факты читаются заново. Ответы API помечены `Cache-Control: no-store`.

Разрешение модели не заменяет предметные права. Например, чтение запасов требует
`inventory.read`, запуск расчёта — `replenishment.run` и `catalogs.read`, создание
черновиков — `orders.write`, `replenishment.read`, `catalogs.read`. Применение пакета
требует `imports.write` и `imports.read`. Корпоративные данные принадлежат одной
компании; многокомпанейная изоляция не добавлялась.

Тексты файлов и результатов инструментов считаются данными, а не командами.
Нет инструментов произвольного shell, SQL, выполнения скриптов, интернет-поиска,
изменения прав, утверждения или отправки заказа поставщику. Серверный allowlist
и бизнес-проверки обязательны даже при наличии инструкции в prompt.

## Загрузка файлов и 1С

Файлы по-прежнему загружаются на `/data` через существующий проверяемый импорт.
Затем пакет выбирается в чате. Прямого прикрепления файла к сообщению, универсального
парсинга любого документа, запуска валидации пакета из чата или создания заказа
непосредственно из произвольного файла нет.

REST-профили собственной 1С настраиваются на `/data/integrations`; агент не получает
инструменты редактирования адреса подключения и credentials. Наличие профиля или
экспорта заказа не подтверждает подключение живой базы партнёра.

## Запуск после обновления

Из корня репозитория, с локальной конфигурацией по [README](../README.md):

```sh
make dev
./scripts/dev.sh exec api alembic upgrade head
```

Новая миграция `75bdae661182` создаёт `ai_conversations`, `ai_messages` и
`ai_proposals`; предыдущая — `5eeb25201444`. Для модели нужна настроенная серверная
конфигурация выбранного провайдера. Ключи не помещать в репозиторий или frontend.
Для расчётов и применения пакетов должны работать worker и Redis. Отсутствие
LLM-конфигурации не превращает детерминированный расчёт в зависимый от модели:
его можно запускать из обычного раздела.

Новый контракт находится под `/api/v1/ai`: `/assistants`, `/knowledge`,
`/conversations`, `/conversations/{id}/messages`,
`/conversations/{id}/proposals/{proposal_id}/decision`. Swagger — `/docs`.
Старый `/ai/chat` оставлен как deprecated-совместимость: требует входа, создаёт
новый личный справочный диалог и не доверяет переданной клиентом истории.

## Повторяемая демонстрация

1. Войдите и откройте `/assistant`. Без разрешения на учётные данные спросите:
   «Где загрузить исходные Excel и что значит готовность пакета?» Проверьте источники.
2. Создайте ещё один диалог, вернитесь к первому и обновите страницу. История должна
   сохраняться; боковая панель использует тот же выбранный диалог.
3. Для демо используйте явно синтетические данные из README. Выберите склад,
   разрешите передачу учётных сводок, выберите «Запасы» и спросите:
   «Покажи остатки и ожидаемые поступления выбранного склада». Проверьте журнал.
4. Выберите «Спрос и расчёт»: «Подготовь расчёт выбранного склада на 22.09.2026».
   Проверьте параметры и подтвердите. Откройте результат на `/recommendations`,
   дождитесь завершения фонового расчёта.
5. Откройте карточку готовой рекомендации и бокового помощника либо передайте её
   UUID в вопросе. Спросите: «Почему рекомендовано это количество?» Ответ должен
   опираться на сохранённый breakdown, а не самостоятельный прогноз модели.
6. Выберите «Заказы»: «Подготовь черновик по рекомендации <UUID>». Проверьте строки.
   До подтверждения заказа нет; после него откройте созданный черновик на `/orders`.
   Не выбирайте уже распределённую или заблокированную рекомендацию.
7. Для проверки отмены подготовьте отдельное предложение и отмените: бизнес-операция
   выполняться не должна. Утверждение/отправка поставщику не входят в этот сценарий.

Это сценарии для повторения; ниже отдельно зафиксирован объём фактической проверки.

## Что проверено при реализации

- 56 профильных тестов: локальный поиск, маршрутизация, запрет чужих инструментов,
  согласие, права, владение диалогом, история, идемпотентность и подтверждения.
- Интеграционные тесты PostgreSQL создают синтетические данные в откатываемых
  транзакциях: до подтверждения заказа нет; после него — один реальный черновик;
  повтор не дублирует, отозванное право блокирует запись. Нет утверждения/отправки.
- Миграция применена на локальном стенде; `alembic check` не находит расхождений.
- В браузере проверены справочный ответ, источники, перезагрузка истории,
  общий диалог страницы/панели и отображение на ширине 1440/375.
- С настроенной моделью выполнен отдельный синтетический smoke-тест:
  координатор → помощник заказов → чтение рекомендации → предложение.
  Коммерческая БД и запись в ней в этом тесте не использовались.
- Проверены Ruff и сборка frontend. Это не backtest на партнёрских данных
  и не подтверждение подключения промышленной 1С.

## Ограничения текущей версии

- Один запрос ждёт модель не более 90 секунд; нет стриминга ответа. При timeout
  или недоступности провайдера показывается ошибка с безопасным повтором.
- Действует лимит 10 сохранённых запросов в минуту на пользователя и один активный
  AI-запрос; помощники не работают параллельно и не запускаются по расписанию.
- В модель попадает ограниченный контекст последних сообщений и текущие сводки,
  не вся история и не весь склад. Большие выборки требуют отдельных вопросов.
- Результат фоновой задачи проверяется в исходном разделе, непрерывного агентного
  наблюдения за worker нет. Сохранённая карточка подтверждения — не live-статус.
- Редактируемые формы в чате, поиск по регламентам пользователя, автоматическое
  восстановление долгих процессов и оценка качества на всех моделях — дальнейшая работа.
- Сохранённые учётные ответы остаются доступны владельцу диалога; механизм удаления
  или отдельной ретенции истории не добавлен.

## Где продолжать разработку

Backend: `Domains/Ai/services/agent_engine.py` — координатор и цикл,
`DTO/agent_tools.py` — профили/схемы/списки разрешений,
`adapters/business_tools.py` — мост к предметным сервисам,
