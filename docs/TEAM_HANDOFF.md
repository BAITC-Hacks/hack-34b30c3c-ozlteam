## 2. Продукт в одном абзаце

Наш единственный пользователь-компания — Электрокомплект; основной человек — менеджер закупа. IEK, Systeme Electric и будущие поставщики поставляют товар на его склад. Спрос — отгрузки Электрокомплекта его клиентам из собственной 1С. Наш сервис принимает продажи, остатки и путь, рассчитывает регулярную потребность с сезонностью, ростом, выбросами и stockout, формирует рекомендации и черновики по поставщикам; менеджер корректирует и утверждает, затем экспортирует. Автоотправка поставщику запрещена. Розничные кассы, управление магазинами и оптимизация доставки не входят в кейс; прежние логистические экраны — наследие прототипа.

Фактическое назначение участников и файлов согласуйте перед параллельными изменениями. Не создавайте дубли готовых страниц: обзор `/`, `/recommendations` и детализация рекомендации, `/orders`, `/data`, `/inventory` уже используют серверный API. `/data/catalogs` поддерживает просмотр, поиск и карточки справочников, но не редактирование. `/recommendations/demo` — отдельный stateless-пример с локальным подтверждением и CSV.

Сопоставление делается **в нашем адаптере и БД**: `(source_id, external_id) → product_id UUIDv7`. Реестр кодов и пакетный адаптер 12 тестовых XLSX реализованы; ограничения повторной синхронизации описаны в [инструкции](partner-workbook-import.md). Файлы двух поставщиков относятся к одной базе Электрокомплекта. Название или похожий артикул не доказывают идентичность или взаимозаменяемость товаров.

## 4. Запуск и сквозная проверка

Нужен Docker с Compose v2. В корне:

```sh
make dev
make seed
./scripts/dev.sh exec api python -m app.seed.replenishment
```

При первом запуске `.env.local` создаётся из шаблона. Для входа задайте `SECURITY_JWT_SECRET` длиной не менее 32 байт и перезапустите API: `./scripts/dev.sh up --build -d api`. Учётная запись разработки — `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` из этого файла. Секреты не коммитить. Приложение по умолчанию: `http://127.0.0.1:5173`; Swagger: `http://127.0.0.1:7575/docs`. Порты можно изменить в `.env.local`.

1. Seed создаёт явно синтетический источник и расчёт на 22.09.2026. Откройте `/data` и `/inventory`, проверьте наличие источника и данных.
2. На `/recommendations` дождитесь готовности расчёта, откройте объяснение, выберите готовые положительные строки и создайте черновики.
3. На `/orders` измените количество с причиной, утвердите через предпросмотр и скачайте CSV/XLSX. Перезагрузите страницу: состояние должно сохраниться.
4. Для 12 исходных книг TrackLogic используйте блок «Пакет исходных Excel из 1С» на `/data`: проверка → готовность → подтверждение применения. Для воспроизводимого тестового наполнения после `make seed` выполните `make seed-excel`; [инструкция сидера](partner-workbook-import.md#сидер-тестовых-excel) описывает зависимости и повтор. Для нормализованного формата действует отдельный контракт [backend-data.md](backend-data.md). Полнота загрузки не означает готовность каждого товара к заказу.
5. Для независимого примера откройте `/recommendations/demo`: демо → обоснование → локальное подтверждение → CSV; отдельно скачайте и загрузите демо-шаблон XLSX. Это не заказ в БД.

Проверки после релевантных изменений:

```sh
make test
./scripts/dev.sh exec frontend npm run build
```

Профильные и интеграционные проверки БД — в `docs/backend-*.md` и README. Не запускайте параллельно тесты, изменяющие общую БД. Готовность задачи: указан покрытый M1–M5 или необходимый ему шаг, пройдены релевантные проверки, объяснены ограничения, документация соответствует коду.

## 5. Что нельзя считать подтверждённым

В реальных выгрузках нет ID клиента, цены, точных stockout-интервалов и подтверждённого lead time. Номер накладной не заменяет клиента; месячные остатки не показывают точную длительность отсутствия. Месячные продажи — сверка с динамикой, не дополнительный спрос. MOQ и кратность — разные условия. Неясные отрицательные строки требуют разбора вида операции; похожие товары не дают права автоматически менять поставщика.

M1–M5 полностью демонстрируем на помеченных синтетических данных; приёмка на реальных данных требует недостающих входов и контрольного расчёта партнёра. Нормализованный API и JSON заказа не равны проверенному промышленному обмену с 1С. Публичного production-развёртывания нет.
