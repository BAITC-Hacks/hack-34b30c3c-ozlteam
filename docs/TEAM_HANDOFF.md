## 1. Что строим

Выбран один кейс трека: **«Автоматический расчёт заказов поставщикам для пополнения склада»**, владелец — ТОО «Электрокомплект» (`ekt.kz`). Пользователь — менеджер отдела закупа. Он загружает данные или открывает демо, запускает расчёт, видит объяснимые рекомендации по артикулам и поставщикам, исправляет количества и утверждает локальный результат перед экспортом. Автоматической отправки поставщику нет.

Первоисточник требований — PDF `HackAlem AI_ Автоматизация формирования заказов поставщикам.docx.pdf` в локальной папке `/Users/sergeyyermolaev/Downloads/TrackLogic/` и одноимённый DOCX в `/Users/sergeyyermolaev/Downloads/All Alem cases/`. Содержательная выжимка и API-контракт — в [replenishment-case.md](replenishment-case.md). [README.md](../README.md) объясняет готовое решение, метод и запуск.

`hackalem_ai_context.txt` в `TrackLogic` — **архивный план строительной AI-платформы**, составленный до смены трека. Не используйте его как постановку текущего кейса. Большая часть [CONTEXT.md](../CONTEXT.md) также хранит историю прототипа; действующее направление указано в верхнем блоке.

## 2. Пять обязательных результатов

| Требование | Что должно измениться в результате |
| --- | --- |
| Базовая потребность | Продажи, остаток, товар в пути, категория/рост и срок поставки влияют на количество. |
| Сезонность и устойчивый рост | Сезонный пик и последовательное повышение спроса учитываются отдельно от среднего за всю историю. |
| Stockout | Дни без товара не трактуются как отсутствие спроса; оценка потерянных продаж повышает потребность. |
| Разовый крупный заказ | Одиночная крупная продажа, в том числе одному обезличенному клиенту, не раздувает регулярный заказ. |
| Итог по поставщикам | Каждая положительная рекомендация показывает количество, срочность и обоснование; интерфейс группирует строки по поставщикам. |

Это критерии из документа кейса, не произвольный roadmap. Подробные проверочные действия — в [таблице приёмки](replenishment-case.md#приёмка-пяти-обязательных-требований).

## 3. Где что реализовано

- `backend/app/Domains/Replenishment/DTO` — структура входа и проверки ссылок между наборами.
- `backend/app/Domains/Replenishment/services` — демонстрационные данные и детерминированный расчёт.
- `backend/app/Domains/Replenishment/adapters/xlsx.py` — импорт и генерация XLSX-шаблона.
- `backend/app/Domains/Replenishment/controllers/http.py` — endpoints `/api/v1/replenishment/*`.
- `backend/tests/test_replenishment.py` — профильные проверки требований.
- `frontend/src/modules/replenishment` — загрузка, расчёт, обзор рекомендаций, правка, локальное подтверждение и CSV.

Расчёт не требует LLM. Общие AI, Notes, бот и прежние логистические экраны остались от заготовки и не составляют решение кейса. Не заявляйте, что OpenAI/NVIDIA вычисляет количество заказа или что есть интеграция с 1С: ни то ни другое в MVP не реализовано.

## 4. Как запустить и показать

Нужен Docker с Compose v2. В корне репозитория:

```sh
make dev
make seed
make test
./scripts/dev.sh exec frontend npm run build
```

При первом `make dev` создаётся локальный `.env.local` из шаблона. Для входа в интерфейс задайте в нём случайный `SECURITY_JWT_SECRET` длиной не менее 32 байт, затем перезапустите API через `./scripts/dev.sh up --build -d api`. Логин и пароль локального администратора берутся из `SEED_ADMIN_EMAIL` и `SEED_ADMIN_PASSWORD` того же файла; они только для разработки. `.env.local`, API-ключи и настоящие данные не коммитить.

Приложение: `http://127.0.0.1:5173`; Swagger: `http://127.0.0.1:7575/docs`. Войдите, откройте «Пополнение склада», дождитесь автоматического расчёта синтетического примера, раскройте объяснения, измените количество, откройте предпросмотр, подтвердите и скачайте CSV. Кнопка «Шаблон XLSX» отдаёт заполненный пример; его можно загрузить обратно. Если порты заняты, измените `FRONTEND_PORT` и `API_PORT` в `.env.local`.

Для API: `GET /api/v1/replenishment/demo` → `POST /api/v1/replenishment/calculate`; `GET /api/v1/replenishment/template` → заполнение шаблона → `POST /api/v1/replenishment/import`. В `README.md` описаны методика расчёта и ограничения.

## 5. Переданные материалы и безопасная работа с ними

Текущая папка локальных материалов — `/Users/sergeyyermolaev/Downloads/TrackLogic/` (прежний путь `.../Track` больше не существует). В ней находятся PDF кейса, старый текстовый контекст и два архива Excel: `IEK.zip`, `Systeme electric.zip`. В каждом архиве по шесть XLSX. В таблице Systeme Electric указан склад `РЦ ЕКТ Рыскулова`, что связывает выгрузку с партнёрским контуром, но не доказывает полноту данных по всему ассортименту. Архивы находятся **только локально**, в Git не загружены.

| Тип выгрузки | IEK | Systeme Electric | Как использовать |
| --- | --- | --- | --- |
| MOQ | `MOQ ИЭК.xlsx`, `Лист7`: код 1С, артикул, минимальная отгрузка; около 1,9 тыс. строк | `MOQ SystemElectric.xlsx`, `Лист_1`: код, артикул, кратность; около 0,6 тыс. строк | Сопоставить SKU и минимальную партию; «кратность» не считать минимумом без уточнения правила поставщика. |
| Динамика продаж | `Динамика продаж_2025-2026.xlsx`, `Лист_1`: около 171,6 тыс. строк | `Динамика продаж_Syseme Electric_2025-2026.xlsx`, `Лист_1`: около 77,3 тыс. строк | Одинаковые поля: дата, номер/тип документа, код, номенклатура, единица, склад, количество. Подходит для дневной истории, но нет цены и клиента. |
| Помесячные остатки | `Ежемесячные остатки продукции за последние 2 года ИЭК.xlsx`, `Лист_1` | `Ежемесячные остатки SystemElectric 2024-2026.xlsx`, `Лист_1` | Код номенклатуры и месяцы 2024–2026; это не текущий остаток по каждому складу и не точный журнал stockout. |
| Помесячные продажи | `Ежемесячные продажи в количественном выражении за последние 2 года.xlsx`, `Лист_1` | `Ежемесячные продажи в кол-м выражении SystemElectric 2024-2026.xlsx`, `Лист_1` | Код и месяцы 2024–2026; полезны для независимой проверки сезонности/тренда по SKU. В Systeme есть дополнительный `Лист1` с общим графиком. |
| Сезонность | `Сезонность ИЭК.xlsx`, `Сезонность` | `Сезонность SystemElectric 2024-2026.xlsx`, `Лист1` | Агрегаты по месяцам и году, не SKU-факторы; нельзя напрямую присвоить коэффициент каждому артикулу. |
| Товары в пути | `Путь ИЭК 22.09.2026.xlsx`, `Лист4`: шесть партий с датами ETA | `Товар в пути_SystemElectric на 22.09.2026.xlsx`, `TDSheet`: 70 колонок, включая категорию, коэффициенты, остатки и «СЭ в пути 24.09» | IEK позволяет разбирать партии по ETA. В Systeme `24.09` в заголовке не принимать за ETA без подтверждения; поле `Заказ` пустое. |

Они не являются готовым входом текущего API. Наш шаблон требует `products`, `suppliers`, `sales`, `stock`, `inbound`, `stockouts`, `category_growth` и опциональный `config` с точными полями из [контракта](replenishment-case.md). В динамике продаж нет готового обезличенного `customer_id` и цены: встречаются реквизиты расходной накладной. Не подставляйте номер или текст документа в `customer_id` без проверки и анонимизации: документ не равен клиенту. Отдельно нужно получить точные периоды stockout, сроки поставки по поставщикам, категории и согласованный прогноз роста. В Systeme `TDSheet` есть коэффициенты по SKU, но они не заменяют объяснимый расчёт и не совпадают напрямую с входом `category_growth`. Нельзя объявлять отсутствие столбца доказательством отсутствия явления.

Перед использованием реальных файлов: подтвердить у владельца данных разрешение и назначение каждой выгрузки; определить, есть ли персональные/коммерчески чувствительные поля; создать локальный адаптер под утверждённую схему; проверить контрольные суммы и даты; запускать расчёт на обезличенной копии. Не прикладывать сырые книги, клиентские документы или ключи к публичному репозиторию. Для разработки и демо используйте синтетический набор из сервиса.

## 6. Что команде делать дальше

1. Сверить столбцы `IEK` и `Systeme Electric` с партнёром и оформить согласованное сопоставление в адаптер, не меняя расчёт ради случайного расположения колонок в Excel.
2. Получить отсутствующие входы: обезличенный клиент, stockout, поставщик и lead time, категории/прирост; узнать формат экспорта, который принимает 1С компании.
3. Проверить рекомендации на контрольных артикулах вместе с менеджером закупа и зафиксировать, где эвристические пороги дают ложные срабатывания.
4. После проверки приватности и сценария продумать production-развёртывание; нынешний Compose предназначен только для локальной разработки.

Не отмечайте пункты как выполненные без подтверждения: это открытые зависимости от данных партнёра и проверки на реальных процессах.
