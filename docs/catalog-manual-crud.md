# Ручное ведение справочников

Справочники на `/data/catalogs` содержат реальные записи PostgreSQL: поставщиков,
склады, категории и товары. Это те же записи, которые используют закупочные
сервисы и AI-помощник. Создание записи не импортирует данные из 1С и не отправляет
изменения в учётную систему.

## Как работать

1. Откройте нужный справочник и добавьте запись. Для всех видов обязательно
   название, для товара также артикул `sku` и базовая единица `unit`.
2. При создании выберите существующий источник, если запись должна относиться
   к уже загруженной базе. Без `source_id` сервер использует источник
   «Ручные справочники Электрокомплект».
3. Для товара укажите поставщика и категорию из **того же источника**. Для заказа
   товар, поставщик и склад также должны принадлежать одному источнику. Ручной
   товар из отдельного ручного источника нельзя смешивать с поставщиком базы 1С.
4. Из карточки измените необходимые поля. `active=false` архивирует запись,
   `active=true` восстанавливает; физического удаления нет.
5. Если другой сотрудник или импорт уже изменил запись, сохранение вернёт 409.
   Обновите карточку, проверьте изменения и повторите своё решение.

Просмотр требует `catalogs.read`, изменение — `catalogs.write`. Наличие кнопки
или доступ к чату не заменяют серверную проверку прав.

## Поля и границы

Ниже поля контракта API; форма показывает основные бизнес-поля. Внешняя ссылка
организации и характеристика доступны через API, но не отдельными полями формы.

- Поставщик: название и активность.
- Склад: название, активность, внешняя ссылка организации при наличии.
- Категория: название, активность, период пересмотра 1–365 дней и страховой запас
  в днях 0–365.
- Товар: название, артикул, код, единица, поставщик, категория, характеристика,
  кратность `pack_size > 0`, минимум `min_order_qty >= 0`, срок поставки 1–730 дней
  либо неизвестный, активность. Количества — до шести знаков после запятой.

Минимальная партия и кратность — разные поля. Переименование товара или ручной
ввод условий не доказывают наличие продаж, свежего остатка или точных stockout.
Импортные ограничения `data_quality` нельзя автоматически считать устранёнными.

## Локальная запись и импортная идентичность

Внутренний UUID генерирует сервер. При ручном создании внешний ID `local:<UUID>`
тоже формируется сервером и не выдаётся за подтверждённую ссылку реальной 1С. PATCH не позволяет
сменить источник или идентичность существующей записи.

Ручная правка импортированной записи — **локальное изменение**, не исправление
исходной базы. Последние импортные `source_revision` и `payload_hash` сохраняются:
повтор той же версии объекта не отменяет ручную правку, а более новая версия
импорта может её перезаписать, включая активность. Архивирование здесь не является
постоянным запретом синхронизации. Согласуйте итоговые изменения в исходной системе.

Архивирование не каскадное: оно не архивирует связанные товары автоматически,
не удаляет историю продаж и не меняет существующие заказы. Проверьте зависимости
и открытые черновики отдельно. Исторические расчёты не пересчитываются задним числом.

Локальные изменения повышают общую ревизию источника и сохраняют аудит в журнале
пакетов обмена: автор, вид объекта, ID, значения до/после. Оптимистическая блокировка
использует `expected_updated_at` из последнего GET, а не придуманную клиентом дату.

## Что увидит AI

Ассистент читает активных поставщиков из БД, а не из списка имён в prompt.
`resolve_supplier` использует этот справочник; товары для черновика ищутся по
поставщику и источнику. Новые сохранённые записи доступны при следующем чтении,
дополнительная регистрация «поставщика для AI» не нужна.

Не переименовывайте демонстрационные записи в реальные для вида. Добавьте
подтверждённого поставщика и его товары вручную либо импортируйте согласованные
данные. Одна пустая карточка поставщика ещё не даёт состав заказа: нужны товары
и склад совместимого источника. Тестовый заказ остаётся явно тестовым; количество
1 в нём не является рассчитанной потребностью.

## API для фронта

Префикс `/api/v1/catalogs`, `kind`: `suppliers`, `warehouses`, `categories`, `products`.

- `POST /{kind}/manual` — бизнес-поля и необязательный `source_id`.
- `PATCH /{kind}/{id}/manual` — изменяемые поля и обязательный `expected_updated_at`.
- Архивирование/восстановление — тот же PATCH с `active`, не DELETE.

Существующие POST/PATCH без `/manual` остаются версионированным контрактом
полной строки источника. Не смешивайте их с формами ручного редактирования.
Актуальные схемы и ошибки — в `/docs` и `/openapi.json`.
