## Можно ли работать без окончательных полей Excel?

**Да. Контракты основных форм уже есть.** Неизвестная структура сырого отчёта партнёра не блокирует работу с нормализованным API. Различаем: поле существует в API; поле присутствует в конкретной выгрузке; бизнес-смысл значения подтверждён. Это три разные проверки.

Снимок проверен по коду `ad3d440` от 23.09.2026. Перед задачей обновить ветку и перепроверить затрагиваемый контракт в `/docs` / `/openapi.json` и DTO. Этот файл — задание на доработку, а не заявление, что перечисленные задачи выполнены.

- **Можно делать сейчас:** фильтры, выбор рекомендаций, комментарий/удаление строки/аудит заказа, обработку ошибок, навигацию и формы на существующих полях.
- **Сначала договориться с backend:** агрегат готовности, реестр сопоставлений, надёжное чтение статуса 1С, признак уже распределённой рекомендации, правила ручной правки данных из 1С.
- **Нужен партнёр для реальных значений:** lead time, единицы и знаки, семантика MOQ/кратности, клиентские ID, stockout. Не требуются для разработки на явно синтетическом наборе.

## Подтверждённые поля основных форм

Все пути API ниже относительно `/api/v1`. ID выбираются из справочников, а не вводятся менеджером вручную. Технические версии/ключи повтора передаёт приложение. Decimal передаём строкой, не округляем исходное значение ради отображения.

| Форма / операция | Поля и ограничения | Контракт |
| --- | --- | --- |
| Зарегистрировать источник | `name`: 1–200 символов; `system`: `1c` или `file`. Не форма логина в 1С, без паролей/сетевых реквизитов. | `CreateSource` в [exchange.py](../backend/app/Domains/Integrations1C/DTO/exchange.py) |
| Проверить файл | `source_id`, `kind`, `file`; дополнительно `column_mapping` — JSON строка→строка, `quantity_multiplier` по подтверждённому соглашению о знаке. CSV UTF-8/XLSX, до 25 МиБ и 10 000 строк. | `POST /imports`, [controller](../backend/app/Domains/DataImports/controllers/http.py) |
| Применить файл | `complete`: boolean, по умолчанию false; true только для финальной части согласованного пакета. Это полнота обмена, не оценка качества. | `POST /imports/{id}/apply` |
| Запустить расчёт | `warehouse_id` обязателен; `category_id` необязателен; `as_of` не в будущем; `parameters.history_days`: 28–3650, default 1095; `idempotency_key`: 1–100 символов. | `POST /replenishment/runs`, [CreateCalculation](../backend/app/Domains/Replenishment/DTO/calculation.py) |
| Создать черновики | `recommendation_ids`: 1–1000 уникальных UUID; `idempotency_key`: 1–128 символов. Поставщик и склад берутся из рекомендаций. | `POST /orders/from-recommendations` |
| Изменить количество | `quantity` > 0, до 20 цифр всего и 6 после точки; `reason`: 1–4000 непустых после trim символов; `expected_version` >= 1. | `PATCH /orders/{id}/lines/{line_id}` |
| Изменить комментарий | `comment`: до 4000, допустима пустая строка; `reason`: 1–4000; `expected_version`. | `PATCH /orders/{id}` |
| Удалить строку | `reason`: 1–4000; `expected_version`; JSON-тело DELETE. Не подменять удаление количеством 0. | `DELETE /orders/{id}/lines/{line_id}` |
| Утвердить | `expected_version`; явное подтверждение состава заказа. Без отправки поставщику и без создания прихода. | `POST /orders/{id}/approve` |

DTO операций заказа: [order.py](../backend/app/Domains/Procurement/DTO/order.py). Полный контракт и права: [backend-procurement.md](backend-procurement.md). Не переносить поля из stateless `CalculationInput` на форму серверного расчёта: это разные сценарии.

## P0 — задания фронту, можно брать сейчас

### FE-01. Завершить отбор рекомендаций и создание черновиков — M5

**Где:** модуль `frontend/src/modules/replenishment`, прежде всего `pages/RunsPage.tsx` и `api/runs.ts`.

- Добавить фильтр поставщика: backend уже принимает `supplier_id` у `GET /replenishment/runs/{id}/recommendations`. Сохранить фильтр в URL, при смене сбрасывать offset и устаревший выбор.
- Добавить «Выбрать доступные на этой странице» для группы поставщика, явно указать границы выбора. `supplier_groups` содержит только текущую страницу; не обещать выбор всего поставщика по всей базе.
- Показывать число выбранных позиций и количество **раздельно по единицам**. Метры и штуки не складывать в один итог; стоимость без цен не показывать.
- Сохранить серверную группировку поставщик + склад и preview перед созданием. Исключить `blocked`, отсутствие поставщика и количество <= 0.
- Повтор после сетевой неопределённости с тем же составом использует тот же ключ; смена состава — новый ключ. После успеха дать ссылки на все полученные черновики: сейчас UI переходит только к первому элементу ответа.
- `RecommendationOut` пока не содержит allocation/order ID: нельзя достоверно выключить все ранее распределённые строки только по этому ответу. Сейчас обработать 409 `already_allocated`, сохранить объяснение; расширение ответа вынести в BE-04 ниже.

**Приёмка:** >50 рекомендаций у нескольких поставщиков; переключение фильтра/страницы не создаёт заказ из скрытого выбора; смешанные единицы не суммируются; двойной клик/повтор запроса не создаёт дубль; конфликт распределения объяснён пользователю.

### FE-02. Комментарий, удаление строки и аудит заказа — M5

**Где:** `frontend/src/modules/orders/{pages/OrdersPage.tsx,api/orders.ts,types.ts}`.

- В карточке черновика добавить форму комментария с причиной изменения по таблице выше.
- У строки добавить действие удаления с причиной и подтверждением. Предупредить: удаление не освобождает рекомендацию для повторного заказа.
- Подключить `GET /orders/{id}/audit?limit&offset`: время, `actor_id`, событие, причина и доступные до/после из `data`. Не выдумывать имя сотрудника, если получен только UUID.
- После изменения брать новую `version` и весь заказ из ответа; в approved нет редактирования. При 409 предложить перечитать документ, не повторять запись автоматически поверх чужой правки; сохранить введённый текст для сравнения.
- Кнопки учитывают `orders.write`, `orders.approve`, `orders.export`; 403 всё равно обрабатывается серверным ответом. Пустой черновик не выдавать за готовый к утверждению.

**Приёмка:** правка комментария → удаление → аудит → утверждение → экспорт; отмена удаления не меняет БД; две вкладки с одной версией дают понятный конфликт; перезагрузка сохраняет результат; утверждённый заказ неизменяем.

### FE-03. Фильтры и контекст переходов — M5

**Где:** модули `orders`, `overview`, `inventory`, `replenishment`.

- В списке заказов подключить существующие серверные `supplier_id` и `warehouse_id`, сохранив `status`, URL и пагинацию. Поиск текста сейчас локальный по странице — честно подписать, не обещать глобальный поиск без endpoint.
- Проверить переход из обзора конкретного склада: получатель должен реально применять фильтр, а не только иметь его в URL. История расчётов поддерживает `warehouse_id` на backend; расширить клиентскую обёртку при необходимости.
- Из рекомендации дать переход к товару/складу в остатках и карточке товара. Обратный переход сохраняет фильтры, страницу и выбранный расчёт; прямой URL имеет fallback.
- Из строки заказа открыть обоснование по её `recommendation_id`; возврат ведёт в тот же заказ. Существующий безопасный список допустимых return-path расширять только под реальные точки входа, не разрешать произвольные внешние адреса.
- Не обрезать справочник молча первыми 200 объектами: использовать имеющуюся пагинацию/поиск там, где выбор выходит за лимит.

**Приёмка:** пройти обзор → расчёт → рекомендация → остатки → назад; склад/товар не меняются, фильтры не теряются. Повторить с прямой ссылкой и справочником более 200 записей.

### FE-04. Понятные формы импорта и запуска — M1

**Где:** `frontend/src/modules/data` и `replenishment`.

- Не переделывать рабочую загрузку; добавить краткую подсказку формата для выбранного `kind` по [DataRow](../backend/app/Domains/DataImports/DTO/rows.py) и [backend-data.md](backend-data.md). Справочники загружаются до ссылающихся фактов.
- Вместо ручного JSON-маппинга можно сделать редактор пар «исходная колонка → поле выбранного kind», сохранив текущий payload. Автоматическое извлечение заголовков требует подтверждённого механизма/контракта; не выдавать эту форму за распознавание широких Excel.
- Показать ошибки лист/строка/поле, число строк, preview и состояние применения. Preview ограничен 20 строками — не подписывать его как полный файл.
- Явно разделить «файл проверен», «данные применены», «пакет завершён». `complete` не ставить молча; сырые широкие XLSX не обещать принять без адаптера.
- Для запуска проверить обязательный склад и дату; при необходимости вывести глубину истории в дополнительных параметрах с границами DTO. Срок поставки/рост/сезонность не добавлять сюда как произвольные поля, которых нет в `CreateCalculation`.
- Сохранить ключ запуска для повторной отправки того же логического запроса после таймаута; новый ключ нужен при новой задаче/изменении параметров. Показать queued/running/done/failed и ошибку, не выдумывать процент прогресса.

**Приёмка:** корректный файл, неверное поле, слишком большой файл, несогласованный mapping, конфликт версии после preview; сбой сети при запуске не создаёт два расчёта. Реальный Excel без адаптера получает честное ограничение, а не фиктивный успех.

### FE-05. Проверить объяснимость, ошибки и демо-путь — M1–M5

**Где:** существующая detail-страница, обзор, общие состояния и навигация.

- Проверить готовые блоки истории/прогноза/выбросов/stockout/пути/формулы на контрольных синтетических позициях; не строить заново уже существующие графики.
- Подписать методы и ограничения: короткая история, отсутствие клиента/stockout, версии источников и дата среза. Нулевое значение, неизвестное значение и ошибка — разные состояния.
- Коды предупреждений перевести в понятный текст, неизвестный код сохранить с нейтральной подписью. «Stockout не отмечен» не равно «дефицита не было»; «выбросы не обнаружены методом» не равно доказанному отсутствию крупных продаж. Подпись о сезонности/тренде должна соответствовать fallback, а не быть постоянным обещанием.
- Проверить 401/403/404/409/422, пустые данные, медленную загрузку, retry и отмену устаревших запросов при смене фильтров.
- Убрать из основного закупочного пути нерелевантные исторические ссылки, если они ещё доступны; `/recommendations/demo` оставить явно отдельной песочницей.

**Приёмка:** основной путь сохраняет расчёт и заказ в БД; demo не выдаётся за сохранённый заказ; цифры на detail совпадают с сохранённым API, а не пересчитываются фронтом. Сборка не заменяет эту проверку.

## P1 — задачи с явной зависимостью, не блокируют P0

### BE-01 / FE-06. Готовность данных

Фронт сейчас может показать существующие ошибки импорта, `source_versions.complete`, предупреждения расчёта и `blocked`. Полноценные статусы «готово / с ограничениями / исправить» требуют серверного агрегата качества.

**К согласованию, не существующий DTO:** область source/warehouse/as_of; число проверенных/сопоставленных/проблемных позиций; покрытие истории и дата остатков; по проблеме — товар/код, правило, тяжесть, источник/лист/строка, причина и допустимое действие; какие проблемы блокируют расчёт или только заказ. Нужны пагинация и согласованная версия результата проверки.

**Разблокировка:** backend публикует endpoint, schema, примеры трёх состояний и правила блокировки. Затем фронт делает список проблем и переход к исправлению. До этого допустим только явно помеченный прототип на тестовых fixtures, не зелёная «готовность» реальных файлов.

### BE-02 / FE-07. Сопоставление сырого отчёта

`column_mapping` существующего импорта лишь переименовывает колонки; он не сопоставляет товары и не разворачивает месячные таблицы.

**К согласованию:** профиль файла/листа, источник 1С, исходный код/характеристика/единица, кандидаты и подтверждённый `external_id`/наш UUID, статус неоднозначности, происхождение строки, сохранение/отмена решения, повторный импорт и права. Это проект контракта, не готовые поля API.

**Разблокировка:** адаптер и реестр backend с примерами совпадения/неизвестного кода/неоднозначности. Партнёр подтверждает единицы/знаки и ключи. Фронт не генерирует UUID товара, не объединяет по имени и не создаёт отдельную «базу IEK» по названию папки.

### BE-03 / FE-08. Ручное редактирование справочников

Поля уже известны: товар — `sku`, `code`, `name`, `unit`, поставщик/категория, `lead_time_days`, `min_order_qty`, `pack_size`, `active`; категория — `review_days`, `safety_days`; поставщик — пока только имя/активность и идентичность источника. В текущей модели lead time и MOQ находятся у товара, не в `SupplierRow`.

Но `POST/PATCH /catalogs/{kind}` — **полная версионированная строка**, не произвольный patch полей: `CatalogCommand` содержит `source_id`, `expected_revision`, `row`; сама `row` — внешний ID, новая revision и остальные поля. Ответы чтения содержат внутренние ссылки, входные строки — внешние. Простое отправление формы чтения обратно неверно.

**Разблокировка:** backend/команда определяет, кто владеет значением — 1С или локальная правка, как разрешается следующий импорт, откуда брать внешние ссылки и версии, как сохраняется происхождение и подтверждённость условий. Пока делаем качественный read-only экран. Defaults MOQ=0/pack_size=1 не обозначаем как подтверждённые поставщиком.

### BE-04. Уже заказанные рекомендации

Для достоверного отключения ранее распределённых строк после перезагрузки нужен согласованный признак allocation и ссылка на заказ в ответе рекомендаций либо отдельный endpoint. Сейчас такого поля в `RecommendationOut` нет. Backend уже защищает от дублей через 409; FE-01 может быть выпущен с этой обработкой, но не обещает полноценную предварительную проверку.

### BE-05 / FE-09. Состояние обмена 1С и новая редакция

Получение пакета утверждённого заказа через `GET /orders/{id}/1c` уже есть; его можно подключить для `orders.export` с подписью «пакет для адаптера, не отправка». Но полноценный экран статусов пока имеет пробел: `OrderOut` не содержит `delivery`, а `/1c` возвращает 409 для rejected/заменённого заказа. Нужен отдельный контракт чтения состояния и связей редакций, доступный и для этих состояний, с согласованными правами.

`POST /orders/{id}/revise` уже принимает `expected_version`, `reason` и создаёт другой draft только после явного rejected. После появления надёжного чтения состояния добавить действие новой редакции и ссылку на предыдущую. `pending` не означает отказ.

`POST /orders/{id}/1c/ack` — интеграционная операция (`revision`, accepted/rejected, `external_document_id`, `message`), не кнопка менеджера «сделать принятым». Поле внешнего документа обязательно для accepted. Не имитировать подтверждение реальной 1С; ручной операторский сценарий требует отдельного решения.

## Общая готовность фронтовой задачи

- Перед UI-изменением применять проектные skills: frontend-modules, project-design, apple-design; для форм/деталей — contextual-back-navigation; для ожидающих карточек — card-loading-skeletons; для API — swagger-openapi. Использовать существующие компоненты, не менять дизайн-систему ради задачи.
- Для каждого блока: initial loading/skeleton, empty, error/retry, success; для действий — pending и защита от дубля. Skeleton повторяет структуру контента; reduced motion, label и ошибки доступны с клавиатуры.
- Проверить узкий экран и desktop, длинные названия/артикулы, дробные количества, более одной страницы. Суммы — только совместимые единицы; Decimal не превращать в неточный payload.
- Запустить `./scripts/dev.sh exec -T frontend npm run build`. Для этого документа изменения приложения не требуются; команду выполняет реализатор после изменения UI.
- Повторить сценарий: нормализованный импорт → расчёт → detail → черновик → правка с причиной → утверждение → экспорт; затем reload, отсутствие права, две вкладки с конфликтующей версией и сетевой повтор. Проверки M1–M5 — в [кейсе](replenishment-case.md).
- Автоматизированный e2e-тест — отдельная задача QA/фронта; сейчас в `frontend/package.json` нет команды e2e. Не заявлять о запуске отсутствующего теста. Синтетические fixtures соответствуют DTO и явно помечены.

## Как передать работу исполнителю

Первый пакет: **FE-01 + FE-02**, затем FE-03/FE-04 и сквозная FE-05. Один владелец записи на модуль: FE-01/FE-04 пересекаются в `replenishment`, FE-02/FE-03 — в `orders`; не запускать их одновременно в одних файлах без согласования. Backend параллельно согласует BE-01…BE-05, адаптер данных отдельно работает с партнёром.

В отчёте по задаче указывать ID, изменённые файлы, подтверждённые поля/API, пройденные проверки и оставшиеся зависимости. Обновлять статус здесь после проверки реализации; наличие endpoint не равно готовности формы. Не ждать всех бизнес-уточнений, чтобы начать P0, и не подменять отсутствующие контракты неподписанными моками.

## Не делать в UI без отдельного решения

- Не отправлять заказ поставщику автоматически.
- Не выдавать экспорт CSV/XLSX или локальное демо-подтверждение за создание документа в 1С.
- Не строить предположения о stockout, lead time, клиенте или единице измерения из неполной выгрузки.
