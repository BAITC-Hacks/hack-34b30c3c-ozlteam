# Кейс «Электрокомплект»: пополнение склада

Рабочая постановка: менеджер закупа Электрокомплекта использует выгрузки собственной 1С — отгрузки клиентам, остатки своего склада, товары в пути и условия закупки. Сервис рассчитывает и объясняет рекомендации по товарам, группирует заказы по поставщикам и оставляет утверждение за человеком. IEK и Systeme Electric — первые поставщики/бренды в данных, не отдельные компании-пользователи или ERP-источники. Число поставщиков не ограничено двумя.

Актуальное направление и границы — [PROJECT_DIRECTION.md](../PROJECT_DIRECTION.md), полный контекст — [CONTEXT.md](../CONTEXT.md), порядок входа команды — [TEAM_HANDOFF.md](TEAM_HANDOFF.md). Не строим розничную кассу, управление магазинами, маршрутизацию доставки или подбор взаимозаменяемого товара по названию. Автоотправка заказа поставщику запрещена.

## Основной сохраняемый сценарий

1. `/data`: зарегистрировать источник, загрузить **нормализованный** CSV/XLSX, просмотреть ошибки и preview, применить проверенный пакет. Регистрация источника не подключает 1С по сети. Сопоставление заголовков не заменяет адаптер реальных широких отчётов.
2. `/inventory`: проверить остатки, путь и интервалы отсутствия по товару и складу.
3. `/recommendations`: запустить расчёт по складу/категории или открыть историю, дождаться завершения фоновой задачи, изучить числа, предупреждения и объяснение.
4. Выбрать положительные рекомендации со статусом `ready` и создать черновики; сервер группирует их по поставщику и складу.
5. `/orders`: скорректировать количество с причиной, проверить и утвердить заказ с контролем версии, выгрузить CSV/XLSX. Заказ и утверждение сохраняются в БД; поставщику ничего автоматически не отправляется.

API сценария: `/api/v1/replenishment/runs`, `/api/v1/recommendations/{id}`, `/api/v1/orders` и `/api/v1/imports`. Подробности: [расчёт](backend-replenishment.md), [данные и 1С](backend-data.md), [заказы](backend-procurement.md). JSON заказа для адаптера 1С доступен через API; создание документа в реальной конфигурации партнёра ещё не проверено. Готовый API не равен готовой промышленной интеграции.

Сопоставление товара выполняется у нас: `(source_id, external_id)` указывает на стабильный внутренний `product_id` UUIDv7. Код 1С из отчёта, GUID и наш UUID — разные идентификаторы. Для 12 исходных книг реализованы [пакетный адаптер и постоянный реестр кодов](partner-workbook-import.md); склад, единицы и условия требуют подтверждения, ведущие нули сохраняются. Этот адаптер не означает подключение реальной базы 1С по сети.

## Контракт демонстрационного интерфейса

Страница `/recommendations/demo` использует отдельные stateless endpoints и требует Bearer-сессию:
`replenishment.read` для demo/template, `replenishment.run` для calculate/import.
Они не создают расчёт или заказ в БД. Серверный сценарий с историей и UUIDv7:
[расчёты](backend-replenishment.md), [данные и 1С](backend-data.md),
[заказы и утверждение](backend-procurement.md). Реальная база 1С ещё не подключена.

`GET /api/v1/replenishment/demo` возвращает демонстрационный набор `CalculationInput`.
`POST /api/v1/replenishment/calculate` принимает его и возвращает `CalculationResult`.
`POST /api/v1/replenishment/import` принимает файл `.xlsx` с листами `products`, `suppliers`, `sales`, `stock`, `inbound`, `stockouts`, `category_growth` и возвращает `CalculationInput`. Необязательный лист `config` хранит `as_of` и `review_days`; без него используются дата последней продажи и 14 дней.

Скачиваемый демонстрационный шаблон использует русские листы и заголовки: «Товары», «Поставщики», «Продажи», «Остатки», «Товары в пути», «Периоды отсутствия», «Прирост по категориям», «Настройки». Импорт принимает и этот формат, и прежний английский. «Как заполнить» поясняет, что данные синтетические и файл не является заказом. На листе «Товары» видно название поставщика; его код сохранён в скрытой колонке D. Название справочное, связь при импорте определяется кодом: для смены поставщика раскройте D и укажите код из листа «Поставщики». Проценты хранятся долями (8% = 0,08), даты — значениями Excel. Шапки закреплены, включены фильтры, перенос текста и ширины по содержимому.
`GET /api/v1/replenishment/template` отдаёт заполненный демонстрационный файл с этими листами.

В `CalculationInput`: `as_of` (дата), `review_days` (период до следующего расчёта), массивы `products`, `suppliers`, `sales`, `stock`, `inbound`, `stockouts`, `category_growth`. Артикул связан с одним предпочтительным поставщиком; расчёт ведётся отдельно по каждому складу.

В `CalculationResult`: `as_of`, `recommendations`. Каждая строка содержит `sku`, `name`, `warehouse`, `category`, `supplier_id`, `supplier_name`, `recommended_qty`, `urgency` (`critical`, `soon`, `normal`), `explanation` и `metrics`: `raw_sales`, `excluded_spike_units`, `lost_demand_units`, `adjusted_daily_demand`, `seasonality_factor`, `trend_factor`, `category_growth_factor`, `on_hand`, `inbound`, `target_stock`, `stock_position`, `lead_days`, `review_days`. Интерфейс группирует строки по поставщикам, разрешает ручную правку количества и экспорт CSV. Утверждение остаётся локальным действием пользователя, заказ поставщику автоматически не отправляется.

Схемы строк:

- `products`: `sku`, `name`, `category`, `supplier_id`.
- `suppliers`: `id`, `name`, `lead_days`, `min_order_qty`.
- `sales`: `date`, `sku`, `warehouse`, `customer_id` (обезличенный), `quantity`, `price`.
- `stock`: `sku`, `warehouse`, `quantity`.
- `inbound`: `sku`, `warehouse`, `quantity`, `eta`.
- `stockouts`: `sku`, `warehouse`, `start`, `end` (включительно).
- `category_growth`: `category`, `growth_pct` (например, `0.08` для 8%).

Методика и пороги обнаружения разовых продаж должны быть изложены в README и проверены тестами для всех пяти обязательных требований.

## Приёмка пяти обязательных требований

| ID | Проверка | Изменение в исходных данных | Ожидаемый результат |
| --- | --- | --- | --- |
| M1 | Базовая потребность | Увеличить остаток либо своевременный приход в пути по одному артикулу; отдельно изменить продажи, категорию/рост и срок поставки | Входы участвуют в расчёте; количество и его числовое объяснение меняются согласно формуле. Для остатка/пути выбрать пример вне порога округления MOQ. |
| M2 | Сезонность и рост | Сопоставить товар с пиком в текущем сезоне и товар с устойчивым ростом за последние месяцы | Прогноз отражает сезон и тренд, а не среднее за весь год. |
| M3 | Отсутствие товара | Добавить подтверждённые дни stockout без продаж в пример с положительным регулярным спросом | Оценка потерянного спроса и потребность растут относительно расчёта по сырым продажам. |
| M4 | Разовый крупный заказ | Добавить одну аномально крупную продажу одному обезличенному клиенту | Регулярное рекомендуемое количество существенно не растёт; исключённый объём виден в объяснении. |
| M5 | Итоговые заказы | Рассчитать все позиции, создать черновики, скорректировать, утвердить и экспортировать | Рекомендации имеют количество, срочность и конкретное обоснование; заказы сгруппированы по поставщику и складу. Утверждение сохраняется, автоотправки нет. |

Для повторяемой проверки используйте явно синтетический набор с несколькими артикулами и указанными эффектами. Серверный seed: `./scripts/dev.sh exec api python -m app.seed.replenishment`; независимый пример: `/recommendations/demo`. Наличие механизма в коде или успешный синтетический тест не доказывают качество прогноза на данных партнёра.

## Ограничения реальных данных и приёмки

Переданные исходники находятся в `TrackLogic/` закрытого командного репозитория; [разбор книг](hackathon/tracklogic.md) фиксирует их поля и неоднозначности. Это сырые отчёты, не формат ни нормализованного `/imports`, ни демо-шаблона `/replenishment/import`.

- Нет обезличенного ID клиента и цены. Нельзя выдавать номер накладной за клиента или утверждать, что проверена история покупок одного клиента.
- Нет точных stockout-интервалов и подтверждённого lead time. Месячный остаток — сигнал для проверки, не установленная длительность отсутствия; возможную приближённую оценку нужно отдельно согласовать и пометить как гипотезу.
- Динамику и месячные продажи сверяем, не суммируем. Внутреннее перемещение не является продажей покупателю; знак количества и возвраты требуют согласованной трактовки.
- MOQ и кратность проверяем раздельно; отсутствие условий или несовпадение кодов отражаем как проблему готовности, а не заполняем выдуманными значениями.
- Экспорт должен быть проверен на образце учётной системы партнёра. Утверждение заказа не создаёт автоматически факт товара в пути или остаток.

При сдаче укажите отдельно: что проверено на синтетике, что рассчитано на реальных данных с ограничениями, что ещё требует уточнения партнёра. Не публикуйте коммерческие исходники и ключи во внешнем публичном доступе.
