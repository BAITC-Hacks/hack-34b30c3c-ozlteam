# Кейс «Электрокомплект»: пополнение склада

Рабочая постановка: менеджер закупа загружает данные о продажах, остатках, товарах в пути, периодах отсутствия и поставщиках; система рассчитывает и объясняет рекомендации по артикулам, группирует их по поставщикам и оставляет утверждение за человеком.

## Контракт демонстрационного интерфейса

Эти stateless endpoints сохранены для интерфейса MVP и требуют Bearer-сессию:
`replenishment.read` для demo/template, `replenishment.run` для calculate/import.
Они не создают расчёт или заказ в БД. Серверный сценарий с историей и UUIDv7:
[расчёты](backend-replenishment.md), [данные и 1С](backend-data.md),
[заказы и утверждение](backend-procurement.md). Реальная база 1С ещё не подключена.

`GET /api/v1/replenishment/demo` возвращает демонстрационный набор `CalculationInput`.
`POST /api/v1/replenishment/calculate` принимает его и возвращает `CalculationResult`.
`POST /api/v1/replenishment/import` принимает файл `.xlsx` с листами `products`, `suppliers`, `sales`, `stock`, `inbound`, `stockouts`, `category_growth` и возвращает `CalculationInput`. Необязательный лист `config` хранит `as_of` и `review_days`; без него используются дата последней продажи и 14 дней.
`GET /api/v1/replenishment/template` отдаёт заполненный демонстрационный файл с этими листами.

В `CalculationInput`: `as_of` (дата), `review_days` (период до следующего расчёта), массивы `products`, `suppliers`, `sales`, `stock`, `inbound`, `stockouts`, `category_growth`. Артикул связан с одним предпочтительным поставщиком; расчёт ведётся отдельно по каждому складу.

В `CalculationResult`: `as_of`, `recommendations`. Каждая строка содержит `sku`, `name`, `warehouse`, `category`, `supplier_id`, `supplier_name`, `recommended_qty`, `urgency` (`critical`, `soon`, `normal`), `explanation` и `metrics`: `raw_sales`, `excluded_spike_units`, `lost_demand_units`, `adjusted_daily_demand`, `seasonality_factor`, `trend_factor`, `category_growth_factor`, `on_hand`, `inbound`, `target_stock`, `stock_position`, `lead_days`, `review_days`. Интерфейс группирует строки по поставщикам, разрешает ручную правку количества и экспорт CSV. Утверждение остаётся локальным действием пользователя, заказ поставщику автоматически не отправляется.

Схемы строк:

- `products`: `sku`, `name`, `category`, `supplier_id`.
- `suppliers`: `id`, `name`, `lead_days`, `min_order_qty`.
- `sales`: `date`, `sku`, `warehouse`, `customer_id` (обезличенный), `quantity`, `price`.
- `stock`: `sku`, `warehouse`, `quantity`.
- `inbound`: `sku`, `warehouse`, `quantity`, `eta`.
- `stockouts`: `sku`, `warehouse`, `start`, `end` (включительно).
- `category_growth`: `category`, `growth_pct` (например, `0.08` для 8%).

Методика и пороги обнаружения разовых продаж должны быть изложены в README и проверены тестами для всех пяти обязательных требований.

## Приёмка пяти обязательных требований

| Проверка | Изменение в исходных данных | Ожидаемый результат |
| --- | --- | --- |
| Базовая потребность | Увеличить остаток либо приход в пути по одному артикулу | Рекомендуемое количество снижается; изменение категории, роста или срока поставки тоже меняет результат. |
| Сезонность и рост | Сопоставить товар с пиком в текущем сезоне и товар с устойчивым ростом за последние месяцы | Прогноз отражает сезон и тренд, а не среднее за весь год. |
| Отсутствие товара | Добавить дни stockout без продаж | Оценка потерянного спроса и потребность растут относительно сырых продаж. |
| Разовый крупный заказ | Добавить одну аномально крупную продажу одному обезличенному клиенту | Регулярное рекомендуемое количество почти не растёт; исключённый объём виден в объяснении. |
| Итоговые заказы | Рассчитать все позиции | Строки разбиты по поставщикам; у каждой есть количество, срочность и конкретное обоснование. |

Для демонстрации достаточно одного синтетического набора с несколькими артикулами и указанными эффектами. Реальная выгрузка V2 партнёра в репозиторий не добавляется до проверки приватности и согласования колонок.
