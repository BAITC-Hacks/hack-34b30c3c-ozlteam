# REST-отчёты собственной 1С

Раздел `/data/integrations` настраивает получение JSON по HTTP GET из собственной
1С Электрокомплекта. Один источник — одна база учёта; в нём можно сохранить несколько
отчётов одного или разных типов. Поставщики не становятся отдельными базами автоматически.
Адреса реальной 1С, учётные данные и формат её HTTP-сервисов ещё требуют согласования.

## Что хранится и где

В PostgreSQL сохраняются профили отчётов: источник, название, тип данных, URL,
путь к массиву JSON, соответствия полей, явно выбранный знак количества и имя
серверной переменной авторизации. Пароля или токена в профиле нет.

Получение отчёта создаёт проверяемый импорт в существующем staging-хранилище:
нормализованные строки, ошибки, количество строк и контрольная сумма. Исходное тело
HTTP-ответа не архивируется. После явного применения строки попадают в существующие
таблицы справочников и фактов; внутренние ID — UUIDv7. Сопоставление имён полей не
заменяет реестр идентичностей `(source_id, external_id)` и не ищет товар по имени.

## Подключение

1. В серверном окружении задайте `ONEC_ALLOWED_ORIGINS` — точные доверенные origin,
   например `https://onec.example.kz`, несколько через запятую. Путь в это значение
   не входит. Пустое значение запрещает исходящие запросы, но позволяет сохранить профиль.
2. Если требуется авторизация, задайте `ONEC_AUTH_EKT` полным значением HTTP-заголовка
   `Authorization`, например `Bearer …` либо `Basic …`. В форме укажите только имя
   `ONEC_AUTH_EKT`. Секрет не вводится в URL, mapping или браузерное хранилище.
3. Локальный Compose передаёт эти две переменные только API. После изменения
   `.env.local` пересоздайте API: `./scripts/dev.sh up -d --no-deps api`.
   Для других имён `ONEC_AUTH_*` требуется явно передать переменную процессу API
   в конфигурации сервера/Compose. Не используйте `VITE_*`.
4. На странице выберите существующий источник либо зарегистрируйте собственную
   базу. Создайте отчёт, укажите его URL, тип и соответствия полей.
5. Сохраните профиль, получите и проверьте строки. Исправьте ошибки до применения.
   Сначала загружайте справочники, затем связанные факты.
6. Примените проверенные строки. «Обмен завершён» отмечайте только на последней
   части согласованной выгрузки всей базы. До этого расчёт по источнику заблокирован.

Разрешённый origin — административная граница доверия: сервер должен иметь сетевой
доступ именно к согласованному HTTP-сервису. Редиректы не выполняются, TLS проверяется,
размер ответа и время запроса ограничены. Приватная сеть 1С поддерживается через
явно разрешённый origin. Сервис не обходит сетевые ограничения или права 1С.
Текущий предел — 25 МиБ и 10 000 строк за получение, общий таймаут — 35 секунд;
ответ должен быть несжатым JSON с HTTP 200.

## Формат и сопоставление

Поддерживаются девять нормализованных типов: категории, поставщики, склады,
номенклатура (включая срок поставки, MOQ и кратность), отгрузки, остатки,
товары в пути, подтверждённые интервалы отсутствия, прогноз прироста.
Обязательность и типы полей выдаёт API из действующих DTO.

Ответ — массив объектов либо объект с массивом по указанному пути, например
`value` для JSON OData или `data.rows`. Пустой путь означает корневой массив.
Пути полей поддерживают вложенные объекты; точное совпадение ключа с точками
проверяется раньше обхода вложенности. В staging попадают только выбранные поля.

Например, JSON-строка справочника поставщиков:

```json
{"Ref_Key":"supplier-1","Version":1,"Description":"Пример поставщика"}
```

Соответствия: `Ref_Key → external_id`, `Version → revision`,
`Description → name`. `revision` — положительная монотонная версия объекта,
а не произвольно назначенная константа. Код номенклатуры, артикул и внешний ID
не взаимозаменяемы; значения с ведущими нулями передаются строками.

Преобразования ограничены сопоставлением полей и явным выбором знака количества
`1` / `-1`. Формулы и произвольный код не исполняются. Единицы и знак операции
требуют согласования; `abs()` ко всем отгрузкам не применяется. Даты/числа должны
удовлетворять [нормализованному контракту](backend-data.md). OData `DataVersion`
нельзя молча считать нашей числовой `revision`.

Этот конструктор не разворачивает широкие месячные колонки, не вычисляет stockout
из месячных остатков и не суммирует детализацию с контрольными месячными итогами.
Для исходных XLSX существует [пакетный адаптер](partner-workbook-import.md).
Для другой формы REST-ответа нужен согласованный нормализующий HTTP-сервис 1С.
Ответ с признаком следующей страницы отклоняется: незавершённую первую страницу
нельзя выдать за полный отчёт. Расписание и автоматический обход страниц пока не реализованы.

## API и проверка

Префикс `/api/v1/integrations/1c`:

- `GET /report-kinds` — доступные виды и поля.
- `GET /sources/{source_id}/reports` — сохранённые профили.
- `POST /sources/{source_id}/reports` — создать профиль.
- `PUT /reports/{report_id}` — заменить настройки профиля.
- `POST /reports/{report_id}/preview` — получить JSON, сопоставить, проверить и сохранить staging.

Применение использует существующий `POST /api/v1/imports/{id}/apply`.
Импорты и их ошибки доступны в общем журнале `/data`. Версии источника,
проверка ссылок, конфликты изменений и защита от повторов работают по общему
[контракту обмена](backend-data.md). Swagger `/docs` и `/openapi.json` описывают
реальные поля, ограничения и права.

Проверки с синтетическими HTTP-ответами доказывают работу адаптера, но не
подтверждают подключение к реальной базе партнёра. Для приёмки нужны её URL,
настройка доступа, пример ответа и контрольные суммы.
