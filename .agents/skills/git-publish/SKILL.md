# Публикация изменений в Git

Этот skill фиксирует согласованный с пользователем workflow. Применяй его по запросу публикации или по командному правилу автопуша из [git-team-workflow](../git-team-workflow/SKILL.md) после завершения и личной проверки всей задачи. Само редактирование файла ещё не означает, что работа готова к публикации.

## Значение команды

- «Залить в гит» / «запушить изменения» без названия ветки: опубликовать изменения в текущей ветке.
- «Запушить изменения в N», если текущая ветка уже N: тот же сценарий одной ветки.
- «Запушить изменения в N», если текущая ветка A: собрать изменения в A, обновить обе ветки с remote, влить N в A, запушить A, перейти на N, влить A в N, запушить N и остаться в N.

Названная команда разрешает необходимые локальные коммиты, fetch, обычные merge, разрешение конфликтов и push в указанные этим workflow ветки. Не спрашивай повторное подтверждение обычных шагов. Не создавай вместо этого PR и не подменяй прямой push другим процессом без причины.

## Проверка исходного состояния

1. Установи корень репозитория, активную ветку, staged/unstaged/untracked изменения, upstream и remote. Прочитай применимые `AGENTS.md`. Проверяй `git status`, diff и историю перед изменениями.
2. Сохрани имя исходной ветки A и её исходный HEAD. Используй эти сохранённые значения после переключений; не вычисляй A заново как «текущую» ветку.
3. Выбирай remote по upstream активной ветки; при отсутствии upstream используй единственный однозначный remote. При нескольких неоднозначных remote уточни выбор. Не печатай URL, содержащие credentials.
4. Если репозиторий не инициализирован, HEAD detached, уже идёт merge/rebase/cherry-pick или целевой remote/ветка отсутствует — не угадывай историю и не начинай несвязанные операции. Уточни недостающие данные. Не создавай новую N вместо запрошенной существующей ветки молча.
5. Просмотри все изменения, включая уже staged и новые файлы. «Все изменения» включает текущую работу пользователя и агента в репозитории; не отбрасывай чужие правки как «не мои».
6. Не включай секреты, рабочие `.env` или игнорируемые файлы. `.env.*.example` можно включать после проверки содержимого. Помни, что `.gitignore` не защищает уже tracked файлы: проверь staged diff. Не используй `git add -f`. Если секрет уже в истории либо без уточнения невозможно сохранить намерение пользователя, сообщи об этом без раскрытия значения секрета; не переписывай историю самовольно.
7. Проверь, какие уже существующие локальные коммиты будут опубликованы вместе с новыми. Не сквошь и не удаляй их, чтобы искусственно получить один коммит на всю ветку. Если найдены явно посторонние коммиты с неясным назначением, уточни область публикации до push.

## Один локальный коммит

Собери все допустимые текущие изменения — добавления, правки и удаления — в один новый локальный коммит с содержательным сообщением по итоговому diff. Перед коммитом проверь staged diff и выполни проверки, относящиеся к изменениям. Не обходи hooks и не подавляй проваленные обязательные проверки.

«Один коммит» относится к текущим изменениям рабочего дерева, а не ко всей предыдущей истории. Последующие merge-коммиты допустимы. Не используй amend/rebase/reset/squash для изменения существующей истории. При отсутствии новых изменений не создавай пустой коммит: синхронизируй и опубликуй уже имеющуюся работу, если она есть.

Запомни SHA созданного коммита. Перед fetch/merge рабочее дерево должно быть чистым; неожиданные новые правки не прячь автоматически в stash и не удаляй.

## Сценарий 1: публикация в текущую ветку A

1. Создай один локальный коммит текущих изменений по правилам выше.
2. Выполни fetch актуальной A с выбранного remote, убедись, что используемый remote-tracking ref действительно обновлён. Не полагайся на старый ref после неудачного fetch.
3. Влей удалённую A в локальную A обычным `git merge`. Fast-forward допустим; при расхождении истории допустим merge-коммит. Не выполняй rebase.
4. Разреши конфликты, заверши merge и проверь результат.
5. Запушь локальную A в удалённую A, явно указывая remote и ветку назначения. Останься в A.

## Сценарий 2: публикация в N из текущей A

Соблюдай порядок; push A до переключения на N является частью пользовательского требования.

1. В A создай один локальный коммит всех текущих допустимых изменений.
2. Скачай актуальные состояния N и A с выбранного remote. Обе операции fetch должны завершиться успешно до интеграции. Зафиксируй актуальные remote-tracking refs.
3. Находясь в A, влей удалённую A в локальную A, разреши конфликты и заверши merge.
4. Влей актуальную удалённую N в A, разреши конфликты и заверши merge. На этом шаге используй именно свежую удалённую N, а не потенциально устаревшую локальную N.
5. Выполни относящиеся к изменениям проверки и запушь A в удалённую A.
6. Только после успешного push A переключись на N. Если локальной N нет, создай tracking-ветку от скачанной удалённой N. Если локальная N существует, сохрани её историю и влей в неё актуальную удалённую N. Не сбрасывай существующую N через `reset --hard` или `switch -C`.
7. Влей сохранённую исходную ветку A в N обычным merge. Разреши конфликты, заверши merge и проверь результат.
8. Запушь N в удалённую N. Останься в N.

## Конфликты и проверки

- Для каждого конфликта прочитай обе стороны и связанный код. Сохраняй смысл обеих доработок; не выбирай массово `ours` или `theirs`.
- Для lock-файлов сначала объедини манифесты зависимостей, затем пересоздай lock штатным менеджером и проверь совместимость. Не склеивай lock-файлы механически.
- Исправления, необходимые для разрешения merge, включай в соответствующий merge-коммит. Если после проверки потребовался отдельный исправляющий коммит, не скрывай его и не переписывай уже опубликованную историю ради количества коммитов.
- Убедись, что не осталось unmerged paths и случайных маркеров конфликтов. Выполни `git diff --check` и подходящие проверки проекта. Для backend/frontend используй команды из README через `./scripts/dev.sh`, чтобы явно выбрать `.env.local`.
- Если конфликт требует неизвестного продуктового решения, задай конкретный вопрос и сохрани текущее состояние. Не выдумывай бизнес-логику ради завершения merge.
- Проверки расширяй при изменениях, конфликтах или новых сбоях; не повторяй весь набор без причины после каждого технического шага.

## Ошибки и изменения remote во время работы

Никогда не используй force push, включая `--force-with-lease`. При non-fast-forward обнови соответствующую удалённую ветку, влей новые изменения в публикуемую локальную ветку, проверь и повтори обычный push. После двух повторных отказов из-за движения remote остановись и сообщи состояние; не продолжай бесконечный цикл.

При ошибке сети, прав доступа, branch protection или hooks сохрани локальные коммиты и сообщи точную причину. Не отключай защиту и не перенастраивай credentials. Если A уже опубликована, а N ещё нет, явно сообщи о частичной публикации: не откатывай A автоматически и не называй весь workflow завершённым.

## Завершение

Проверь чистоту рабочего дерева, отсутствие незавершённых Git-операций и успешную публикацию нужных коммитов. После fetch опубликованный локальный tip должен совпадать с remote tip или быть его предком, если remote уже продвинулся. В двухветочном сценарии проверь, что N включает слитый tip A.

В ответе кратко укажи:

- SHA и смысл коммита текущих изменений;
- какие ветки опубликованы и в какой ветке осталось рабочее дерево;
- были ли конфликты и какие проверки выполнены;
- точную незавершённую часть, если публикация заблокирована.
