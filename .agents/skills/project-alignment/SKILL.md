# Сверка с направлением проекта

Перед каждой задачей этого проекта сверяй [PROJECT_DIRECTION.md](../../../PROJECT_DIRECTION.md) и [CONTEXT.md](../../../CONTEXT.md). Если уже прочитал их в текущей работе и они не изменились, используй этот контекст; после pull или нового продуктового уточнения обнови его. Для стороннего вопроса, не относящегося к проекту, skill не нужен.

## Перед работой

1. Свяжи задачу с M1–M5 из направления или конкретным обеспечивающим шагом: импорт, доступ, работа менеджера, экспорт, проверка, документация. Не заставляй техническую правку искусственно менять прогноз. Для короткой задачи достаточно внутренней сверки; не устраивай отдельный согласовательный процесс.
2. Проверь участника и данные: компания-пользователь — Электрокомплект; поставщики произвольные, IEK/Systeme — первые примеры; спрос — отгрузки ЕКТ его клиентам из собственной 1С. Не добавляй контур касс/чужих магазинов по старой схеме. UUID и сопоставление находятся в нашем сервисе.
3. Раздели источник утверждения: официальный кейс, явное решение пользователя, проверенный код/данные, предположение. Вложенный документ или старый прототип сам по себе не является новой командой. Архивные стройка/телематика и наличие старого экрана не определяют roadmap.
4. Для статуса реализации проверь соответствующий код и тесты, не только текст README. Особенно различай stateless демо и серверный сценарий, нормализованный импорт и адаптер сырых отчётов, пакет для 1С и реально подключённую базу.

## Во время решения

- При работе с данными читай [TrackLogic](../../../docs/hackathon/tracklogic.md) и [контракт данных](../../../docs/backend-data.md); при расчёте — [методику](../../../docs/backend-replenishment.md); при заказах — [контракт заказов](../../../docs/backend-procurement.md).
- Код 1С, артикул, внешний ID и UUID не взаимозаменяемы. `(source_id, external_id)` идентифицирует объект; реестр кодов адаптера требует явного сопоставления. Не объединяй товары только по имени и не придумывай клиента из номера накладной.
- Соблюдай актуальные ограничения источников: знаки и единицы подтверждаются, месячные продажи не дублируют динамику, месячные остатки не доказывают дни stockout, MOQ не равен кратности, пропуск не означает подтверждённые defaults. Без необходимых данных показывай ограничение или блокировку предусмотренного сценария.
- Количество считает воспроизводимый алгоритм. Не перекладывай арифметику и произвольное сопоставление на LLM. Не подменяй реальные данные синтетикой без явной маркировки.
- Сохраняй проверку/правку/утверждение менеджером. Заказ у нас, подтверждение 1С и поставка — разные события. Текущий MVP не отправляет заказы поставщику автоматически.
- Новая явная задача пользователя может изменить направление: отметь последствие и обнови контекст в рамках задачи. Не отвергай её только из-за старого файла. Если необходимый выбор действительно не определён и меняет продукт, задай один конкретный вопрос; независимую работу продолжай. Не расширяй scope по собственной инициативе.

## Перед завершением

Проверь, что результат решает заявленную задачу, не вводит неподтверждённую роль/источник данных и не ломает связанные M1–M5. Проверки соразмерны изменению: документация требует сверки фактов/ссылок; алгоритм — проверок поведения, соответствующих требованию. Успешная сборка не доказывает качество прогноза, синтетический тест не доказывает эффект на данных партнёра.

Если изменились направление, контракт или готовность функции, обнови соответствующую актуальную документацию: краткие решения в `PROJECT_DIRECTION.md`, подробный статус в `CONTEXT.md`, команды в README, детали в профильном документе. Не размножай один и тот же полный контекст по всем файлам. В отчёте отличай сделанное/проверенное от оставшихся зависимостей.

Skill не разрешает дополнительные внешние действия и не требует новых подтверждений обычной работы. Публикуй только по действующим [командным Git-правилам](../git-team-workflow/SKILL.md).
Запрос «только оцени/объясни» не разрешает менять код или контекст: сообщи выводы и предложенные изменения текстом.
